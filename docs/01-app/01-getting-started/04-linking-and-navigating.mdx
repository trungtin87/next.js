Trong Next.js, các routes được render trên server theo mặc định. Điều này thường có nghĩa là client phải đợi phản hồi từ server trước khi một route mới có thể được hiển thị. Next.js đi kèm với các tính năng tích hợp sẵn như [prefetching](#prefetching), [streaming](#streaming), và [client-side transitions](#client-side-transitions) đảm bảo việc điều hướng luôn nhanh chóng và phản hồi tốt.

Hướng dẫn này giải thích cách điều hướng hoạt động trong Next.js và cách bạn có thể tối ưu hóa nó cho [dynamic routes](#dynamic-routes-without-loadingtsx) và [mạng chậm](#slow-networks).

## Cách điều hướng hoạt động

Để hiểu cách điều hướng hoạt động trong Next.js, sẽ hữu ích khi làm quen với các khái niệm sau:

- [Server Rendering](#server-rendering)
- [Prefetching](#prefetching)
- [Streaming](#streaming)
- [Client-side transitions](#client-side-transitions)

### Server Rendering

Trong Next.js, [Layouts và Pages](/docs/app/getting-started/layouts-and-pages) là [React Server Components](https://react.dev/reference/rsc/server-components) theo mặc định. Trong lần điều hướng ban đầu và các lần tiếp theo, [Server Component Payload](/docs/app/getting-started/server-and-client-components#how-do-server-and-client-components-work-in-nextjs) được tạo trên server trước khi được gửi đến client.

Có hai loại server rendering, dựa trên _thời điểm_ nó xảy ra:

- **Static Rendering (hoặc Prerendering)** xảy ra tại build time hoặc trong quá trình [revalidation](/docs/app/getting-started/caching-and-revalidating) và kết quả được cache.
- **Dynamic Rendering** xảy ra tại request time để phản hồi lại yêu cầu của client.

Sự đánh đổi của server rendering là client phải đợi server phản hồi trước khi route mới có thể được hiển thị. Next.js giải quyết độ trễ này bằng cách [prefetching](#prefetching) các routes mà người dùng có khả năng truy cập và thực hiện [client-side transitions](#client-side-transitions).

> **Lưu ý**: HTML cũng được tạo cho lần truy cập đầu tiên.

### Prefetching

Prefetching là quá trình tải một route trong background trước khi người dùng điều hướng đến nó. Điều này làm cho việc điều hướng giữa các routes trong ứng dụng của bạn cảm thấy tức thì, bởi vì vào thời điểm người dùng nhấp vào một liên kết, dữ liệu để render route tiếp theo đã có sẵn ở phía client.

Next.js tự động prefetches các routes được liên kết với [`<Link>` component](/docs/app/api-reference/components/link) khi chúng đi vào viewport của người dùng.

```tsx filename="app/layout.tsx" switcher
import Link from 'next/link'

export default function Layout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <nav>
          {/* Prefetched when the link is hovered or enters the viewport */}
          <Link href="/blog">Blog</Link>
          {/* No prefetching */}
          <a href="/contact">Contact</a>
        </nav>
        {children}
      </body>
    </html>
  )
}
```

```jsx filename="app/layout.js" switcher
import Link from 'next/link'

export default function Layout() {
  return (
    <html>
      <body>
        <nav>
          {/* Prefetched when the link is hovered or enters the viewport */}
          <Link href="/blog">Blog</Link>
          {/* No prefetching */}
          <a href="/contact">Contact</a>
        </nav>
        {children}
      </body>
    </html>
  )
}
```

Bao nhiêu phần của route được prefetched phụ thuộc vào việc nó là static hay dynamic:

- **Static Route**: toàn bộ route được prefetched.
- **Dynamic Route**: prefetching bị bỏ qua, hoặc route được prefetched một phần nếu [`loading.tsx`](/docs/app/api-reference/file-conventions/loading) hiện diện.

Bằng cách bỏ qua hoặc prefetching một phần các dynamic routes, Next.js tránh công việc không cần thiết trên server cho các routes mà người dùng có thể không bao giờ truy cập. Tuy nhiên, việc đợi phản hồi từ server trước khi điều hướng có thể mang lại cho người dùng ấn tượng rằng ứng dụng không phản hồi.

### Streaming

Streaming cho phép server gửi các phần của một dynamic route đến client ngay khi chúng sẵn sàng, thay vì đợi toàn bộ route được render. Điều này có nghĩa là người dùng nhìn thấy thứ gì đó sớm hơn, ngay cả khi các phần của trang vẫn đang tải.

Đối với dynamic routes, điều đó có nghĩa là chúng có thể được **prefetched một phần**. Tức là, các shared layouts và loading skeletons có thể được yêu cầu trước thời hạn.

Đằng sau hậu trường, Next.js sẽ tự động bọc nội dung `page.tsx` trong một `<Suspense>` boundary. Fallback UI đã được prefetched sẽ được hiển thị trong khi route đang tải, và được thay thế bằng nội dung thực tế khi sẵn sàng.

> **Lưu ý**: Bạn cũng có thể sử dụng [`<Suspense>`](https://react.dev/reference/react/Suspense) để tạo loading UI cho các nested components.

Lợi ích của `loading.tsx`:

- Điều hướng tức thì và phản hồi trực quan cho người dùng.
- Shared layouts vẫn tương tác được và việc điều hướng có thể bị gián đoạn.
- Cải thiện Core Web Vitals: [TTFB](https://web.dev/articles/ttfb), [FCP](https://web.dev/articles/fcp), và [TTI](https://web.dev/articles/tti).

Để cải thiện hơn nữa trải nghiệm điều hướng, Next.js thực hiện một [client-side transition](#client-side-transitions) với component `<Link>`.

### Client-side transitions

Theo truyền thống, việc điều hướng đến một trang server-rendered kích hoạt tải lại toàn bộ trang. Điều này xóa trạng thái, đặt lại vị trí cuộn và chặn tương tác.

Next.js tránh điều này với client-side transitions sử dụng component `<Link>`. Thay vì tải lại trang, nó cập nhật nội dung một cách linh hoạt bằng cách:

- Giữ lại bất kỳ shared layouts và UI nào.
- Thay thế trang hiện tại bằng trạng thái loading đã được prefetched hoặc một trang mới nếu có sẵn.

Client-side transitions là thứ làm cho các ứng dụng server-rendered _cảm thấy_ giống như các ứng dụng client-rendered. Và khi kết hợp với [prefetching](#prefetching) và [streaming](#streaming), nó cho phép chuyển đổi nhanh chóng, ngay cả đối với các dynamic routes.

## Điều gì có thể làm cho transitions chậm?

Những tối ưu hóa này của Next.js làm cho việc điều hướng nhanh chóng và phản hồi tốt. Tuy nhiên, trong một số điều kiện nhất định, transitions vẫn có thể _cảm thấy_ chậm. Dưới đây là một số nguyên nhân phổ biến và cách cải thiện trải nghiệm người dùng:

### Dynamic routes không có `loading.tsx`

Khi điều hướng đến một dynamic route, client phải đợi phản hồi từ server trước khi hiển thị kết quả. Điều này có thể mang lại cho người dùng ấn tượng rằng ứng dụng không phản hồi.

Chúng tôi khuyên bạn nên thêm `loading.tsx` vào các dynamic routes để kích hoạt partial prefetching, kích hoạt điều hướng tức thì và hiển thị loading UI trong khi route renders.

```tsx filename="app/blog/[slug]/loading.tsx" switcher
export default function Loading() {
  return <LoadingSkeleton />
}
```

```jsx filename="app/blog/[slug]/loading.js" switcher
export default function Loading() {
  return <LoadingSkeleton />
}
```

> **Lưu ý**: Trong chế độ development, bạn có thể sử dụng Next.js Devtools để xác định xem route là static hay dynamic. Xem [`devIndicators`](/docs/app/api-reference/config/next-config-js/devIndicators) để biết thêm thông tin.

### Dynamic segments không có `generateStaticParams`

Nếu một [dynamic segment](/docs/app/api-reference/file-conventions/dynamic-routes) có thể được prerendered nhưng không được vì thiếu [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params), route sẽ fallback về dynamic rendering tại request time.

Đảm bảo route được tạo tĩnh tại build time bằng cách thêm `generateStaticParams`:

```tsx filename="app/blog/[slug]/page.tsx" switcher
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())

  return posts.map((post) => ({
    slug: post.slug,
  }))
}

export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  // ...
}
```

```jsx filename="app/blog/[slug]/page.js" switcher
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())

  return posts.map((post) => ({
    slug: post.slug,
  }))

export default async function Page({ params }) {
  const { slug } = await params
  // ...
}
```

### Mạng chậm

Trên các mạng chậm hoặc không ổn định, prefetching có thể không hoàn thành trước khi người dùng nhấp vào một liên kết. Điều này có thể ảnh hưởng đến cả static và dynamic routes. Trong những trường hợp này, fallback `loading.js` có thể không xuất hiện ngay lập tức vì nó chưa được prefetched.

Để cải thiện perceived performance, bạn có thể sử dụng [`useLinkStatus` hook](/docs/app/api-reference/functions/use-link-status) để hiển thị phản hồi ngay lập tức trong khi quá trình chuyển đổi đang diễn ra.

```tsx filename="app/ui/loading-indicator.tsx" switcher
'use client'

import { useLinkStatus } from 'next/link'

export default function LoadingIndicator() {
  const { pending } = useLinkStatus()
  return (
    <span aria-hidden className={`link-hint ${pending ? 'is-pending' : ''}`} />
  )
}
```

```jsx filename="app/ui/loading-indicator.js" switcher
'use client'

import { useLinkStatus } from 'next/link'

export default function LoadingIndicator() {
  const { pending } = useLinkStatus()
  return (
    <span aria-hidden className={`link-hint ${pending ? 'is-pending' : ''}`} />
  )
}
```

Bạn có thể "debounce" gợi ý bằng cách thêm độ trễ hoạt ảnh ban đầu (ví dụ: 100ms) và bắt đầu ở trạng thái vô hình (ví dụ: `opacity: 0`). Điều này có nghĩa là chỉ báo tải sẽ chỉ được hiển thị nếu việc điều hướng mất nhiều thời gian hơn độ trễ đã chỉ định. Xem [tham khảo `useLinkStatus`](/docs/app/api-reference/functions/use-link-status#gracefully-handling-fast-navigation) để biết ví dụ CSS.

> **Lưu ý**: Bạn có thể sử dụng các mẫu phản hồi trực quan khác như thanh tiến trình. Xem ví dụ [tại đây](https://github.com/vercel/react-transition-progress).

### Vô hiệu hóa prefetching

Bạn có thể chọn không tham gia prefetching bằng cách đặt prop `prefetch` thành `false` trên component `<Link>`. Điều này hữu ích để tránh sử dụng tài nguyên không cần thiết khi render danh sách lớn các liên kết (ví dụ: bảng cuộn vô hạn).

```tsx
<Link prefetch={false} href="/blog">
  Blog
</Link>
```

Tuy nhiên, việc vô hiệu hóa prefetching đi kèm với sự đánh đổi:

- **Static routes** sẽ chỉ được fetch khi người dùng nhấp vào liên kết.
- **Dynamic routes** sẽ cần được render trên server trước khi client có thể điều hướng đến nó.

Để giảm sử dụng tài nguyên mà không vô hiệu hóa hoàn toàn prefetch, bạn có thể chỉ prefetch khi hover. Điều này giới hạn prefetching cho các routes mà người dùng có nhiều _khả năng_ truy cập hơn, thay vì tất cả các liên kết trong viewport.

```tsx filename="app/ui/hover-prefetch-link.tsx" switcher
'use client'

import Link from 'next/link'
import { useState } from 'react'

function HoverPrefetchLink({
  href,
  children,
}: {
  href: string
  children: React.ReactNode
}) {
  const [active, setActive] = useState(false)

  return (
    <Link
      href={href}
      prefetch={active ? null : false}
      onMouseEnter={() => setActive(true)}
    >
      {children}
    </Link>
  )
}
```


### Hydration chưa hoàn tất

`<Link>` là một Client Component và phải được hydrated trước khi nó có thể prefetch routes. Trong lần truy cập đầu tiên, các gói JavaScript lớn có thể làm chậm quá trình hydration, ngăn cản prefetching bắt đầu ngay lập tức.

React giảm thiểu điều này với Selective Hydration và bạn có thể cải thiện điều này hơn nữa bằng cách:

- Sử dụng plugin [`@next/bundle-analyzer`](/docs/app/guides/package-bundling#analyzing-javascript-bundles) để xác định và giảm kích thước gói bằng cách loại bỏ các dependencies lớn.
- Di chuyển logic từ client sang server nếu có thể. Xem tài liệu [Server và Client Components](/docs/app/getting-started/server-and-client-components) để được hướng dẫn.

## Ví dụ

### Native History API

Next.js cho phép bạn sử dụng các phương thức [`window.history.pushState`](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState) và [`window.history.replaceState`](https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState) native để cập nhật ngăn xếp lịch sử của trình duyệt mà không cần tải lại trang.

Các lệnh gọi `pushState` và `replaceState` tích hợp vào Next.js Router, cho phép bạn đồng bộ hóa với [`usePathname`](/docs/app/api-reference/functions/use-pathname) và [`useSearchParams`](/docs/app/api-reference/functions/use-search-params).

#### `window.history.pushState`

Sử dụng nó để thêm một mục mới vào ngăn xếp lịch sử của trình duyệt. Người dùng có thể điều hướng quay lại trạng thái trước đó. Ví dụ, để sắp xếp danh sách sản phẩm:

```tsx fileName="app/ui/sort-products.tsx" switcher
'use client'

import { useSearchParams } from 'next/navigation'

export default function SortProducts() {
  const searchParams = useSearchParams()

  function updateSorting(sortOrder: string) {
    const params = new URLSearchParams(searchParams.toString())
    params.set('sort', sortOrder)
    window.history.pushState(null, '', `?${params.toString()}`)
  }

  return (
    <>
      <button onClick={() => updateSorting('asc')}>Sort Ascending</button>
      <button onClick={() => updateSorting('desc')}>Sort Descending</button>
    </>
  )
}
```


#### `window.history.replaceState`

Sử dụng nó để thay thế mục hiện tại trên ngăn xếp lịch sử của trình duyệt. Người dùng không thể điều hướng quay lại trạng thái trước đó. Ví dụ, để chuyển đổi locale của ứng dụng:

```tsx fileName="app/ui/locale-switcher.tsx" switcher
'use client'

import { usePathname } from 'next/navigation'

export function LocaleSwitcher() {
  const pathname = usePathname()

  function switchLocale(locale: string) {
    // e.g. '/en/about' or '/fr/contact'
    const newPath = `/${locale}${pathname}`
    window.history.replaceState(null, '', newPath)
  }

  return (
    <>
      <button onClick={() => switchLocale('en')}>English</button>
      <button onClick={() => switchLocale('fr')}>French</button>
    </>
  )
}
```
