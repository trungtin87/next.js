[React Server Components](https://react.dev/reference/rsc/server-components) cải thiện hiệu suất và đơn giản hóa việc tìm nạp dữ liệu, nhưng cũng thay đổi vị trí và cách thức truy cập dữ liệu, thay đổi một số giả định bảo mật truyền thống để xử lý dữ liệu trong các ứng dụng frontend.

Hướng dẫn này sẽ giúp bạn hiểu cách suy nghĩ về bảo mật dữ liệu trong Next.js và cách triển khai các phương pháp hay nhất.

## Các phương pháp tìm nạp dữ liệu

Có ba phương pháp chính mà chúng tôi khuyên dùng để tìm nạp dữ liệu trong Next.js, tùy thuộc vào quy mô và tuổi của dự án của bạn:

- [API HTTP](#api-http-ben-ngoai): cho các ứng dụng và tổ chức lớn hiện có.
- [Lớp truy cập dữ liệu](#lop-truy-cap-du-lieu): cho các dự án mới.
- [Truy cập dữ liệu cấp thành phần](#truy-cap-du-lieu-cap-thanh-phan): để tạo mẫu và học tập.

Chúng tôi khuyên bạn nên chọn một phương pháp tìm nạp dữ liệu và tránh trộn lẫn chúng. Điều này giúp các nhà phát triển làm việc trong cơ sở mã của bạn và các kiểm toán viên bảo mật hiểu rõ những gì sẽ xảy ra.

### API HTTP bên ngoài

Bạn nên tuân theo mô hình **Zero Trust** khi áp dụng Server Components trong một dự án hiện có. Bạn có thể tiếp tục gọi các điểm cuối API hiện có của mình như REST hoặc GraphQL từ Server Components bằng cách sử dụng [`fetch`](/docs/app/api-reference/functions/fetch), giống như cách bạn làm trong Client Components.

```tsx filename="app/page.tsx"
import { cookies } from 'next/headers'

export default async function Page() {
  const cookieStore = cookies()
  const token = cookieStore.get('AUTH_TOKEN')?.value

  const res = await fetch('https://api.example.com/profile', {
    headers: {
      Cookie: `AUTH_TOKEN=${token}`,
      // Other headers
    },
  })

  // ....
}
```

Cách tiếp cận này hoạt động tốt khi:

- Bạn đã có sẵn các thực hành bảo mật.
- Các nhóm backend riêng biệt sử dụng các ngôn ngữ khác hoặc quản lý API một cách độc lập.

### Lớp truy cập dữ liệu

Đối với các dự án mới, chúng tôi khuyên bạn nên tạo một **Lớp truy cập dữ liệu (DAL)** chuyên dụng. Đây là một thư viện nội bộ kiểm soát cách thức và thời điểm dữ liệu được tìm nạp và những gì được chuyển đến ngữ cảnh hiển thị của bạn.

Một Lớp truy cập dữ liệu nên:

- Chỉ chạy trên máy chủ.
- Thực hiện kiểm tra ủy quyền.
- Trả về **Đối tượng truyền dữ liệu (DTO)** an toàn, tối thiểu.

Cách tiếp cận này tập trung tất cả logic truy cập dữ liệu, giúp thực thi truy cập dữ liệu nhất quán dễ dàng hơn và giảm nguy cơ lỗi ủy quyền. Bạn cũng nhận được lợi ích của việc chia sẻ bộ nhớ đệm trong bộ nhớ trên các phần khác nhau của một yêu cầu.

```ts filename="data/auth.ts"
import { cache } from 'react'
import { cookies } from 'next/headers'

// Các phương thức trợ giúp được lưu trong bộ nhớ đệm giúp dễ dàng nhận được cùng một giá trị ở nhiều nơi
// mà không cần truyền thủ công. Điều này không khuyến khích việc truyền nó từ Server
// Component sang Server Component, giúp giảm thiểu nguy cơ truyền nó đến Client
// Component.
export const getCurrentUser = cache(async () => {
  const token = cookies().get('AUTH_TOKEN')
  const decodedToken = await decryptAndValidate(token)
  // Không bao gồm các mã thông báo bí mật hoặc thông tin cá nhân dưới dạng các trường công khai.
  // Sử dụng các lớp để tránh vô tình chuyển toàn bộ đối tượng cho máy khách.
  return new User(decodedToken.id)
})
```

```tsx filename="data/user-dto.tsx"
import 'server-only'
import { getCurrentUser } from './auth'

function canSeeUsername(viewer: User) {
  // Thông tin công khai hiện tại, nhưng có thể thay đổi
  return true
}

function canSeePhoneNumber(viewer: User, team: string) {
  // Quy tắc về quyền riêng tư
  return viewer.isAdmin || team === viewer.team
}

export async function getProfileDTO(slug: string) {
  // Không truyền giá trị, đọc lại các giá trị được lưu trong bộ nhớ đệm, cũng giải quyết được bối cảnh và dễ dàng thực hiện nó một cách lười biếng

  // sử dụng API cơ sở dữ liệu hỗ trợ tạo khuôn mẫu truy vấn an toàn
  const [rows] = await sql`SELECT * FROM user WHERE slug = ${slug}`
  const userData = rows[0]

  const currentUser = await getCurrentUser()

  // chỉ trả về dữ liệu liên quan cho truy vấn này chứ không phải mọi thứ
  // <https://www.w3.org/2001/tag/doc/APIMinimization>
  return {
    username: canSeeUsername(currentUser) ? userData.username : null,
    phonenumber: canSeePhoneNumber(currentUser, userData.team)
      ? userData.phonenumber
      : null,
  }
}
```

```tsx filename="app/page.tsx"
import { getProfile } from '../../data/user'

export async function Page({ params: { slug } }) {
  // Trang này hiện có thể truyền hồ sơ này một cách an toàn khi biết
  // rằng nó không được chứa bất kỳ thông tin nhạy cảm nào.
  const profile = await getProfile(slug);
  ...
}
```

> **Cần biết:** Các khóa bí mật nên được lưu trữ trong các biến môi trường, nhưng chỉ Lớp truy cập dữ liệu mới được truy cập `process.env`. Điều này giúp các bí mật không bị lộ ra các phần khác của ứng dụng.

### Truy cập dữ liệu cấp thành phần

Để tạo mẫu và lặp lại nhanh chóng, các truy vấn cơ sở dữ liệu có thể được đặt trực tiếp trong Server Components.

Tuy nhiên, cách tiếp cận này giúp dễ dàng vô tình làm lộ dữ liệu cá nhân cho máy khách, ví dụ:

```tsx filename="app/page.tsx"
import Profile from './components/profile.tsx'

export async function Page({ params: { slug } }) {
  const [rows] = await sql`SELECT * FROM user WHERE slug = ${slug}`
  const userData = rows[0]
  // LỘ RA: Điều này làm lộ tất cả các trường trong userData cho máy khách vì
  // chúng ta đang truyền dữ liệu từ Server Component đến Client.
  return <Profile user={userData} />
}
```

```tsx filename="app/ui/profile.tsx"
'use client'

// XẤU: Đây là một giao diện props tồi vì nó chấp nhận nhiều dữ liệu hơn mức cần thiết của
// Client Component và nó khuyến khích các thành phần máy chủ truyền tất cả
// dữ liệu đó xuống. Một giải pháp tốt hơn sẽ là chấp nhận một đối tượng giới hạn chỉ với
// các trường cần thiết để hiển thị hồ sơ.
export default async function Profile({ user }: { user: User }) {
  return (
    <div>
      <h1>{user.name}</h1>
      ...
    </div>
  )
}
```

Bạn nên khử trùng dữ liệu trước khi chuyển nó đến Client Component:

```ts filename="data/user.ts"
import { sql } from './db'

export async function getUser(slug: string) {
  const [rows] = await sql`SELECT * FROM user WHERE slug = ${slug}`
  const user = rows[0]

  // Chỉ trả về các trường công khai
  return {
    name: user.name,
  }
}
```

```tsx filename="app/page.tsx"
import { getUser } from '../data/user'
import Profile from './ui/profile'

export default async function Page({
  params: { slug },
}: {
  params: { slug: string }
}) {
  const publicProfile = await getUser(slug)
  return <Profile user={publicProfile} />
}
```

## Đọc dữ liệu

### Truyền dữ liệu từ máy chủ đến máy khách

Khi tải ban đầu, cả Server và Client Components đều chạy trên máy chủ để tạo HTML. Tuy nhiên, chúng thực thi trong các hệ thống mô-đun bị cô lập. Điều này đảm bảo rằng Server Components có thể truy cập dữ liệu và API riêng tư, trong khi Client Components không thể.

**Server Components:**

- Chỉ chạy trên máy chủ.
- Có thể truy cập an toàn các biến môi trường, bí mật, cơ sở dữ liệu và API nội bộ.

**Client Components:**

- Chạy trên máy chủ trong quá trình kết xuất trước, nhưng phải tuân theo các giả định bảo mật giống như mã chạy trong trình duyệt.
- Không được truy cập dữ liệu đặc quyền hoặc các mô-đun chỉ dành cho máy chủ.

Điều này đảm bảo ứng dụng được bảo mật theo mặc định, nhưng có thể vô tình làm lộ dữ liệu cá nhân thông qua cách dữ liệu được tìm nạp hoặc chuyển đến các thành phần.

### Tainting

Để ngăn chặn việc vô tình làm lộ dữ liệu riêng tư cho máy khách, bạn có thể sử dụng React Taint API:

- [`experimental_taintObjectReference`](https://react.dev/reference/react/experimental_taintObjectReference) cho các đối tượng dữ liệu.
- [`experimental_taintUniqueValue`](https://react.dev/reference/react/experimental_taintUniqueValue) cho các giá trị cụ thể.

Bạn có thể bật việc sử dụng trong ứng dụng Next.js của mình bằng tùy chọn [`experimental.taint`](/docs/app/api-reference/config/next-config-js/taint) trong `next.config.js`:

```js filename="next.config.js"
module.exports = {
  experimental: {
    taint: true,
  },
}
```

Điều này ngăn các đối tượng hoặc giá trị bị nhiễm độc được chuyển đến máy khách. Tuy nhiên, đây là một lớp bảo vệ bổ sung, bạn vẫn nên lọc và khử trùng dữ liệu trong [DAL](#data-access-layer) của mình trước khi chuyển nó đến ngữ cảnh hiển thị của React.

> **Cần biết:**
>
> - Theo mặc định, các biến môi trường chỉ có sẵn trên Máy chủ. Next.js hiển thị bất kỳ biến môi trường nào có tiền tố `NEXT_PUBLIC_` cho máy khách. [Tìm hiểu thêm](/docs/app/guides/environment-variables).
> - Các hàm và lớp đã bị chặn không cho chuyển đến Client Components theo mặc định.

### Ngăn chặn việc thực thi mã chỉ dành cho máy chủ phía máy khách

Để ngăn mã chỉ dành cho máy chủ thực thi trên máy khách, bạn có thể đánh dấu một mô-đun bằng gói [`server-only`](https://www.npmjs.com/package/server-only):

```bash package="npm"
npm install server-only
```

```bash package="yarn"
yarn add server-only
```

```bash package="pnpm"
pnpm add server-only
```

```bash package="bun"
bun add server-only
```

```ts filename="lib/data.ts"
import 'server-only'

//...
```

Điều này đảm bảo rằng mã độc quyền hoặc logic kinh doanh nội bộ vẫn ở trên máy chủ bằng cách gây ra lỗi xây dựng nếu mô-đun được nhập trong môi trường máy khách.

## Thay đổi dữ liệu

Next.js xử lý các thay đổi bằng [Server Actions](https://react.dev/reference/rsc/server-functions).

### Các tính năng bảo mật tích hợp sẵn của Server Actions

Theo mặc định, khi một Server Action được tạo và xuất, nó sẽ tạo một điểm cuối HTTP công khai và phải được xử lý với các giả định bảo mật và kiểm tra ủy quyền tương tự. Điều này có nghĩa là, ngay cả khi một Server Action hoặc hàm tiện ích không được nhập ở nơi khác trong mã của bạn, nó vẫn có thể truy cập công khai.

Để cải thiện bảo mật, Next.js có các tính năng tích hợp sau:

- **ID hành động an toàn:** Next.js tạo các ID được mã hóa, không xác định để cho phép máy khách tham chiếu và gọi Server Action. Các ID này được tính toán lại định kỳ giữa các bản dựng để tăng cường bảo mật.
- **Loại bỏ mã chết:** Các Server Actions không sử dụng (được tham chiếu bởi ID của chúng) sẽ bị xóa khỏi gói máy khách để tránh truy cập công khai.

> **Cần biết**:
>
> Các ID được tạo trong quá trình biên dịch và được lưu vào bộ nhớ đệm trong tối đa 14 ngày. Chúng sẽ được tạo lại khi một bản dựng mới được bắt đầu hoặc khi bộ nhớ đệm của bản dựng bị vô hiệu.
> Cải tiến bảo mật này giúp giảm thiểu rủi ro trong trường hợp thiếu lớp xác thực. Tuy nhiên, bạn vẫn nên coi Server Actions như các điểm cuối HTTP công khai.

```jsx
// app/actions.js
'use server'

// Nếu hành động này **được** sử dụng trong ứng dụng của chúng tôi, Next.js
// sẽ tạo một ID an toàn để cho phép máy khách tham chiếu
// và gọi Server Action.
export async function updateUserAction(formData) {}

// Nếu hành động này **không được** sử dụng trong ứng dụng của chúng tôi, Next.js
// sẽ tự động xóa mã này trong quá trình `next build`
// và sẽ không tạo điểm cuối công khai.
export async function deleteUserAction(formData) {}
```

### Xác thực đầu vào của máy khách

Bạn phải luôn xác thực đầu vào từ máy khách, vì chúng có thể dễ dàng bị sửa đổi. Ví dụ: dữ liệu biểu mẫu, tham số URL, tiêu đề và searchParams:

```tsx filename="app/page.tsx"
// XẤU: Tin tưởng trực tiếp vào searchParams
export default async function Page({ searchParams }) {
  const isAdmin = searchParams.get('isAdmin')
  if (isAdmin === 'true') {
    // Dễ bị tấn công: dựa vào dữ liệu máy khách không đáng tin cậy
    return <AdminPanel />
  }
}

// TỐT: Xác minh lại mỗi lần
import { cookies } from 'next/headers'
import { verifyAdmin } from './auth'

export default async function Page() {
  const token = cookies().get('AUTH_TOKEN')
  const isAdmin = await verifyAdmin(token)

  if (isAdmin) {
    return <AdminPanel />
  }
}
```

### Xác thực và ủy quyền

Bạn phải luôn đảm bảo rằng người dùng được ủy quyền để thực hiện một hành động. Ví dụ:

```tsx filename="app/actions.ts"
'use server'

import { auth } from './lib'

export function addItem() {
  const { user } = auth()
  if (!user) {
    throw new Error('Bạn phải đăng nhập để thực hiện hành động này')
  }

  // ...
}
```

Tìm hiểu thêm về [Xác thực](/docs/app/guides/authentication) trong Next.js.

### Bao đóng và mã hóa

Việc định nghĩa một Server Action bên trong một thành phần sẽ tạo ra một [bao đóng](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Closures) trong đó hành động có quyền truy cập vào phạm vi của hàm bên ngoài. Ví dụ, hành động `publish` có quyền truy cập vào biến `publishVersion`:

```tsx filename="app/page.tsx" switcher
export default async function Page() {
  const publishVersion = await getLatestVersion();

  async function publish() {
    "use server";
    if (publishVersion !== await getLatestVersion()) {
      throw new Error('Phiên bản đã thay đổi kể từ khi nhấn xuất bản');
    }
    ...
  }

  return (
    <form>
      <button formAction={publish}>Xuất bản</button>
    </form>
  );
}
```

```jsx filename="app/page.js" switcher
export default async function Page() {
  const publishVersion = await getLatestVersion();

  async function publish() {
    "use server";
    if (publishVersion !== await getLatestVersion()) {
      throw new Error('Phiên bản đã thay đổi kể từ khi nhấn xuất bản');
    }
    ...
  }

  return (
    <form>
      <button formAction={publish}>Xuất bản</button>
    </form>
  );
}
```

Bao đóng hữu ích khi bạn cần ghi lại một _ảnh chụp nhanh_ dữ liệu (ví dụ: `publishVersion`) tại thời điểm kết xuất để có thể sử dụng sau này khi hành động được gọi.

Tuy nhiên, để điều này xảy ra, các biến được ghi lại sẽ được gửi đến máy khách và quay lại máy chủ khi hành động được gọi. Để ngăn dữ liệu nhạy cảm bị lộ cho máy khách, Next.js tự động mã hóa các biến được đóng lại. Một khóa riêng tư mới được tạo cho mỗi hành động mỗi khi một ứng dụng Next.js được xây dựng. Điều này có nghĩa là các hành động chỉ có thể được gọi cho một bản dựng cụ thể.

> **Cần biết:** Chúng tôi không khuyên bạn chỉ dựa vào mã hóa để ngăn các giá trị nhạy cảm bị lộ trên máy khách.

### Ghi đè khóa mã hóa (nâng cao)

Khi tự lưu trữ ứng dụng Next.js của bạn trên nhiều máy chủ, mỗi phiên bản máy chủ có thể có một khóa mã hóa khác nhau, dẫn đến sự không nhất quán tiềm tàng.

Để giảm thiểu điều này, bạn có thể ghi đè khóa mã hóa bằng cách sử dụng biến môi trường `process.env.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`. Việc chỉ định biến này đảm bảo rằng các khóa mã hóa của bạn ổn định qua các bản dựng và tất cả các phiên bản máy chủ đều sử dụng cùng một khóa. Biến này **phải** được mã hóa AES-GCM.

Đây là một trường hợp sử dụng nâng cao trong đó hành vi mã hóa nhất quán trên nhiều lần triển khai là rất quan trọng đối với ứng dụng của bạn. Bạn nên xem xét các thực hành bảo mật tiêu chuẩn như luân chuyển và ký khóa.

> **Cần biết:** Các ứng dụng Next.js được triển khai lên Vercel sẽ tự động xử lý việc này.

### Nguồn gốc được phép (nâng cao)

Vì Server Actions có thể được gọi trong phần tử `<form>`, điều này khiến chúng dễ bị tấn công [CSRF](https://developer.mozilla.org/en-US/docs/Glossary/CSRF).

Ở hậu trường, Server Actions sử dụng phương thức `POST` và chỉ phương thức HTTP này mới được phép gọi chúng. Điều này ngăn chặn hầu hết các lỗ hổng CSRF trong các trình duyệt hiện đại, đặc biệt là với [cookie SameSite](https://web.dev/articles/samesite-cookies-explained) là mặc định.

Như một biện pháp bảo vệ bổ sung, Server Actions trong Next.js cũng so sánh tiêu đề [Origin](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Origin) với tiêu đề [Host](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Host) (hoặc `X-Forwarded-Host`). Nếu chúng không khớp, yêu cầu sẽ bị hủy bỏ. Nói cách khác, Server Actions chỉ có thể được gọi trên cùng một máy chủ với trang lưu trữ nó.

Đối với các ứng dụng lớn sử dụng proxy ngược hoặc kiến trúc backend nhiều lớp (trong đó API máy chủ khác với miền sản xuất), bạn nên sử dụng tùy chọn cấu hình [`serverActions.allowedOrigins`](/docs/app/api-reference/config/next-config-js/serverActions) để chỉ định một danh sách các nguồn gốc an toàn. Tùy chọn chấp nhận một mảng các chuỗi.

```js filename="next.config.js"
/** @type {import('next').NextConfig} */
module.exports = {
  experimental: {
    serverActions: {
      allowedOrigins: ['my-proxy.com', '*.my-proxy.com'],
    },
  },
}
```

Tìm hiểu thêm về [Bảo mật và Server Actions](https://nextjs.org/blog/security-nextjs-server-components-actions).

### Tránh các tác dụng phụ trong quá trình kết xuất

Các đột biến (ví dụ: đăng xuất người dùng, cập nhật cơ sở dữ liệu, vô hiệu hóa bộ nhớ đệm) không bao giờ được là tác dụng phụ, dù là trong Server hay Client Components. Next.js ngăn chặn rõ ràng việc đặt cookie hoặc kích hoạt xác thực lại bộ nhớ đệm trong các phương thức kết xuất để tránh các tác dụng phụ không mong muốn.

```tsx filename="app/page.tsx"
// XẤU: Kích hoạt một đột biến trong quá trình kết xuất
export default async function Page({ searchParams }) {
  if (searchParams.get('logout')) {
    cookies().delete('AUTH_TOKEN')
  }

  return <UserProfile />
}
```

Thay vào đó, bạn nên sử dụng Server Actions để xử lý các đột biến.

```tsx filename="app/page.tsx"
// TỐT: Sử dụng Server Actions để xử lý các đột biến
import { logout } from './actions'

export default function Page() {
  return (
    <>
      <UserProfile />
      <form action={logout}>
        <button type="submit">Đăng xuất</button>
      </form>
    </>
  )
}
```

> **Cần biết:** Next.js sử dụng các yêu cầu `POST` để xử lý các đột biến. Điều này ngăn chặn các tác dụng phụ ngẫu nhiên từ các yêu cầu GET, giảm rủi ro Giả mạo yêu cầu trên nhiều trang web (CSRF).

## Kiểm toán

Nếu bạn đang thực hiện kiểm toán một dự án Next.js, đây là một vài điều chúng tôi khuyên bạn nên xem xét kỹ hơn:

- **Lớp truy cập dữ liệu:** Có một thực hành đã được thiết lập cho một Lớp truy cập dữ liệu bị cô lập không? Xác minh rằng các gói cơ sở dữ liệu và biến môi trường không được nhập bên ngoài Lớp truy cập dữ liệu.
- **Tệp `"use client"`:** Các đạo cụ Thành phần có mong đợi dữ liệu riêng tư không? Các chữ ký kiểu có quá rộng không?
- **Tệp `"use server"`:** Các đối số Hành động có được xác thực trong hành động hoặc bên trong Lớp truy cập dữ liệu không? Người dùng có được ủy quyền lại bên trong hành động không?
- **`/[param]/.`** Các thư mục có dấu ngoặc là đầu vào của người dùng. Các tham số có được xác thực không?
- **`proxy.ts` và `route.ts`:** Có rất nhiều quyền lực. Dành thêm thời gian để kiểm toán chúng bằng các kỹ thuật truyền thống. Thực hiện Kiểm tra thâm nhập hoặc Quét lỗ hổng thường xuyên hoặc phù hợp với vòng đời phát triển phần mềm của nhóm bạn.
