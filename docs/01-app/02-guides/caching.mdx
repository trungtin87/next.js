Next.js cải thiện hiệu suất ứng dụng của bạn và giảm chi phí bằng cách caching công việc rendering và các yêu cầu dữ liệu. Trang này cung cấp cái nhìn sâu sắc về các cơ chế caching của Next.js, các API bạn có thể sử dụng để định cấu hình chúng và cách chúng tương tác với nhau.

> **Thông tin hữu ích**: Trang này giúp bạn hiểu cách Next.js hoạt động "dưới nắp capo" nhưng **không** phải là kiến thức thiết yếu để làm việc hiệu quả với Next.js. Hầu hết các heuristic caching của Next.js được xác định bởi việc sử dụng API của bạn và có các giá trị mặc định cho hiệu suất tốt nhất với cấu hình bằng không hoặc tối thiểu. Nếu bạn muốn chuyển sang các ví dụ, [bắt đầu tại đây](/docs/app/getting-started/fetching-data).

## Tổng quan

Dưới đây là tổng quan cấp cao về các cơ chế caching khác nhau và mục đích của chúng:

| Cơ chế                                      | Cái gì                     | Ở đâu  | Mục đích                                                 | Thời lượng                               |
| ------------------------------------------- | -------------------------- | ------ | -------------------------------------------------------- | ---------------------------------------- |
| [Request Memoization](#request-memoization) | Giá trị trả về của các hàm | Server | Tái sử dụng dữ liệu trong React Component tree           | Vòng đời mỗi yêu cầu                     |
| [Data Cache](#data-cache)                   | Dữ liệu                    | Server | Lưu trữ dữ liệu qua các yêu cầu người dùng và triển khai | Bền vững (có thể revalidate)             |
| [Full Route Cache](#full-route-cache)       | HTML và RSC payload        | Server | Giảm chi phí rendering và cải thiện hiệu suất            | Bền vững (có thể revalidate)             |
| [Router Cache](#client-side-router-cache)   | RSC Payload                | Client | Giảm yêu cầu server khi điều hướng                       | Phiên người dùng hoặc dựa trên thời gian |

Theo mặc định, Next.js sẽ cache nhiều nhất có thể để cải thiện hiệu suất và giảm chi phí. Điều này có nghĩa là các routes được **statically rendered** và các yêu cầu dữ liệu được **cached** trừ khi bạn chọn không tham gia (opt out). Sơ đồ dưới đây hiển thị hành vi caching mặc định: khi một route được statically rendered tại build time và khi một static route được truy cập lần đầu tiên.

Hành vi caching thay đổi tùy thuộc vào việc route được render tĩnh hay động, dữ liệu được cache hay không cache, và liệu yêu cầu là một phần của lần truy cập đầu tiên hay điều hướng tiếp theo. Tùy thuộc vào trường hợp sử dụng của bạn, bạn có thể định cấu hình hành vi caching cho các routes và yêu cầu dữ liệu riêng lẻ.

Fetch caching **không** được hỗ trợ trong `proxy`. Bất kỳ fetch nào được thực hiện bên trong `proxy` của bạn sẽ không được cache.

## Chiến lược Rendering

Để hiểu cách caching hoạt động trong Next.js, sẽ hữu ích khi hiểu các chiến lược rendering có sẵn. Chiến lược rendering xác định khi nào HTML của route của bạn được tạo, điều này ảnh hưởng trực tiếp đến những gì có thể được cache.

### Static Rendering

Với Static Rendering, các routes được render tại **build time** hoặc trong nền sau khi [data revalidation](/docs/app/guides/incremental-static-regeneration). Kết quả được cache và có thể được sử dụng lại qua các yêu cầu. Các static routes được cache đầy đủ trong [Full Route Cache](#full-route-cache).

### Dynamic Rendering

Với Dynamic Rendering, các routes được render tại **request time**. Điều này xảy ra khi route của bạn sử dụng thông tin cụ thể theo yêu cầu như cookies, headers, hoặc search params.

Một route trở thành dynamic khi nó sử dụng bất kỳ API nào sau đây:

- [`cookies`](/docs/app/api-reference/functions/cookies)
- [`headers`](/docs/app/api-reference/functions/headers)
- [`connection`](/docs/app/api-reference/functions/connection)
- [`draftMode`](/docs/app/api-reference/functions/draft-mode)
- [`searchParams` prop](/docs/app/api-reference/file-conventions/page#searchparams-optional)
- [`unstable_noStore`](/docs/app/api-reference/functions/unstable_noStore)
- [`fetch`](/docs/app/api-reference/functions/fetch) với `{ cache: 'no-store' }`

Dynamic routes không được cache trong Full Route Cache, nhưng vẫn có thể sử dụng [Data Cache](#data-cache) cho các yêu cầu dữ liệu.

> **Thông tin hữu ích**: Bạn có thể sử dụng [Cache Components](/docs/app/getting-started/cache-components) để kết hợp static và dynamic rendering trong cùng một route.

## Request Memoization

Next.js mở rộng [`fetch` API](#fetch) để tự động **memoize** các yêu cầu có cùng URL và tùy chọn. Điều này có nghĩa là bạn có thể gọi một hàm fetch cho cùng một dữ liệu ở nhiều nơi trong React component tree trong khi chỉ thực thi nó một lần.

<Image
  alt="Deduplicated Fetch Requests"
  srcLight="/docs/light/deduplicated-fetch-requests.png"
  srcDark="/docs/dark/deduplicated-fetch-requests.png"
  width="1600"
  height="857"
/>

Ví dụ, nếu bạn cần sử dụng cùng một dữ liệu trong một route (ví dụ: trong Layout, Page, và nhiều components), bạn không cần phải fetch dữ liệu ở đầu tree, và chuyển props giữa các components. Thay vào đó, bạn có thể fetch dữ liệu trong các components cần nó mà không phải lo lắng về tác động hiệu suất của việc thực hiện nhiều yêu cầu qua mạng cho cùng một dữ liệu.

```tsx filename="app/example.tsx" switcher
async function getItem() {
  // The `fetch` function is automatically memoized and the result
  // is cached
  const res = await fetch('https://.../item/1')
  return res.json()
}

// This function is called twice, but only executed the first time
const item = await getItem() // cache MISS

// The second call could be anywhere in your route
const item = await getItem() // cache HIT
```

```jsx filename="app/example.js" switcher
async function getItem() {
  // The `fetch` function is automatically memoized and the result
  // is cached
  const res = await fetch('https://.../item/1')
  return res.json()
}

// This function is called twice, but only executed the first time
const item = await getItem() // cache MISS

// The second call could be anywhere in your route
const item = await getItem() // cache HIT
```

**Cách Request Memoization hoạt động**

<Image
  alt="Sơ đồ hiển thị cách fetch memoization hoạt động trong quá trình render React."
  srcLight="/docs/light/request-memoization.png"
  srcDark="/docs/dark/request-memoization.png"
  width="1600"

- Trong khi render một route, lần đầu tiên một yêu cầu cụ thể được gọi, kết quả của nó sẽ không có trong bộ nhớ và nó sẽ là một cache `MISS`.
- Do đó, hàm sẽ được thực thi, và dữ liệu sẽ được fetch từ nguồn bên ngoài, và kết quả sẽ được lưu trữ trong bộ nhớ.
- Các lệnh gọi hàm tiếp theo của yêu cầu trong cùng một lần render pass sẽ là một cache `HIT`, và dữ liệu sẽ được trả về từ bộ nhớ mà không cần thực thi hàm.
- Khi route đã được render và rendering pass hoàn tất, bộ nhớ được "reset" và tất cả các mục request memoization bị xóa.

> **Thông tin hữu ích**:
>
> - Request memoization là một tính năng của React, không phải tính năng của Next.js. Nó được đưa vào đây để hiển thị cách nó tương tác với các cơ chế caching khác.
> - Memoization chỉ áp dụng cho phương thức `GET` trong các yêu cầu `fetch`.
> - Memoization chỉ áp dụng cho React Component tree, điều này có nghĩa là:
>   - Nó áp dụng cho các yêu cầu `fetch` trong `generateMetadata`, `generateStaticParams`, Layouts, Pages, và các Server Components khác.
>   - Nó không áp dụng cho các yêu cầu `fetch` trong Route Handlers vì chúng không phải là một phần của React component tree.
> - Đối với các trường hợp `fetch` không phù hợp (ví dụ: một số database clients, CMS clients, hoặc GraphQL clients), bạn có thể sử dụng [hàm React `cache`](#react-cache-function) để memoize các hàm.

### Thời lượng

Cache tồn tại trong suốt thời gian tồn tại của một yêu cầu server cho đến khi React component tree đã hoàn tất rendering.

### Revalidating

Vì memoization không được chia sẻ giữa các yêu cầu server và chỉ áp dụng trong quá trình rendering, nên không cần phải revalidate nó.

### Opting out

Memoization chỉ áp dụng cho phương thức `GET` trong các yêu cầu `fetch`, các phương thức khác, chẳng hạn như `POST` và `DELETE`, không được memoized. Hành vi mặc định này là một tối ưu hóa của React và chúng tôi không khuyên bạn nên chọn không tham gia (opt out) nó.

Để quản lý các yêu cầu riêng lẻ, bạn có thể sử dụng thuộc tính [`signal`](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/signal) từ [`AbortController`](https://developer.mozilla.org/en-US/docs/Web/API/AbortController).

```js filename="app/example.js"
const { signal } = new AbortController()
fetch(url, { signal })
```

## Data Cache

Next.js có một Data Cache tích hợp sẵn giúp **duy trì** kết quả của các lần fetch dữ liệu qua các **yêu cầu server** đến và **các lần triển khai**. Điều này có thể thực hiện được vì Next.js mở rộng `fetch` API gốc để cho phép mỗi yêu cầu trên server đặt ngữ nghĩa caching bền vững của riêng nó.

> **Thông tin hữu ích**: Trong trình duyệt, tùy chọn `cache` của `fetch` cho biết cách một yêu cầu sẽ tương tác với HTTP cache của trình duyệt, trong Next.js, tùy chọn `cache` cho biết cách một yêu cầu phía server sẽ tương tác với Data Cache của server.

Bạn có thể sử dụng các tùy chọn [`cache`](#fetch-optionscache) và [`next.revalidate`](#fetch-optionsnextrevalidate) của `fetch` để định cấu hình hành vi caching.

Trong chế độ phát triển, dữ liệu `fetch` được [tái sử dụng cho Hot Module Replacement (HMR)](/docs/app/api-reference/functions/fetch#fetch-default-auto-no-store-and-cache-no-store-not-showing-fresh-data-in-development), và các tùy chọn caching bị bỏ qua cho [hard refreshes](/docs/app/api-reference/functions/fetch#hard-refresh-and-caching-in-development).

**Cách Data Cache hoạt động**

- Lần đầu tiên một yêu cầu `fetch` với tùy chọn `'force-cache'` được gọi trong quá trình rendering, Next.js kiểm tra Data Cache để tìm phản hồi đã được cache.
- Nếu tìm thấy phản hồi đã được cache, nó được trả về ngay lập tức và [được memoized](#request-memoization).
- Nếu không tìm thấy phản hồi đã được cache, yêu cầu được thực hiện đến nguồn dữ liệu, kết quả được lưu trữ trong Data Cache, và được memoized.
- Đối với dữ liệu không được cache (ví dụ: không có tùy chọn `cache` được xác định hoặc sử dụng `{ cache: 'no-store' }`), kết quả luôn được fetch từ nguồn dữ liệu, và được memoized.
- Cho dù dữ liệu được cache hay không được cache, các yêu cầu luôn được memoized để tránh thực hiện các yêu cầu trùng lặp cho cùng một dữ liệu trong một React render pass.

> **Sự khác biệt giữa Data Cache và Request Memoization**
>
> Trong khi cả hai cơ chế caching đều giúp cải thiện hiệu suất bằng cách tái sử dụng dữ liệu đã được cache, Data Cache bền vững qua các yêu cầu đến và các lần triển khai, trong khi memoization chỉ tồn tại trong suốt thời gian tồn tại của một yêu cầu.

### Thời lượng

Data Cache bền vững qua các yêu cầu đến và các lần triển khai trừ khi bạn revalidate hoặc opt-out.

### Revalidating

Dữ liệu đã được cache có thể được revalidate theo hai cách, với:

- **Time-based Revalidation**: Revalidate dữ liệu sau khi một khoảng thời gian nhất định đã trôi qua và một yêu cầu mới được thực hiện. Điều này hữu ích cho dữ liệu thay đổi không thường xuyên và độ mới không quá quan trọng.
- **On-demand Revalidation:** Revalidate dữ liệu dựa trên một sự kiện (ví dụ: gửi biểu mẫu). On-demand revalidation có thể sử dụng phương pháp dựa trên tag hoặc dựa trên path để revalidate các nhóm dữ liệu cùng một lúc. Điều này hữu ích khi bạn muốn đảm bảo dữ liệu mới nhất được hiển thị càng sớm càng tốt (ví dụ: khi nội dung từ headless CMS của bạn được cập nhật).

#### Time-based Revalidation

Để revalidate dữ liệu theo khoảng thời gian định giờ, bạn có thể sử dụng tùy chọn `next.revalidate` của `fetch` để đặt thời gian tồn tại cache của một tài nguyên (tính bằng giây).

```js
// Revalidate at most every hour
fetch('https://...', { next: { revalidate: 3600 } })
```

Ngoài ra, bạn có thể sử dụng [các tùy chọn Route Segment Config](#segment-config-options) để định cấu hình tất cả các yêu cầu `fetch` trong một segment hoặc cho các trường hợp bạn không thể sử dụng `fetch`.

- Bất kỳ yêu cầu nào được gọi trong khung thời gian đã chỉ định (ví dụ: 60 giây) sẽ trả về dữ liệu đã được cache.

### Opting out

Nếu bạn _không_ muốn cache phản hồi từ `fetch`, bạn có thể làm như sau:

```js
let data = await fetch('https://api.vercel.app/blog', { cache: 'no-store' })
```

## Full Route Cache

> **Các thuật ngữ liên quan**:
>
> Bạn có thể thấy các thuật ngữ **Automatic Static Optimization**, **Static Site Generation**, hoặc **Static Rendering** được sử dụng thay thế cho nhau để đề cập đến quá trình rendering và caching các routes của ứng dụng của bạn tại build time.

Next.js tự động render và cache các routes tại build time. Đây là một tối ưu hóa cho phép bạn phục vụ route đã được cache thay vì render trên server cho mỗi yêu cầu, dẫn đến tải trang nhanh hơn.

Để hiểu cách Full Route Cache hoạt động, sẽ hữu ích khi xem cách React xử lý rendering, và cách Next.js cache kết quả:

### 1. React Rendering trên Server

Trên server, Next.js sử dụng các API của React để điều phối rendering. Công việc rendering được chia thành các phần: theo các phân đoạn routes riêng lẻ và Suspense boundaries.

Mỗi phần được render theo hai bước:

1. React render các Server Components thành một định dạng dữ liệu đặc biệt, được tối ưu hóa cho streaming, được gọi là **React Server Component Payload**.
2. Next.js sử dụng React Server Component Payload và các hướng dẫn JavaScript của Client Component để render **HTML** trên server.

Điều này có nghĩa là chúng ta không phải đợi mọi thứ render xong trước khi cache công việc hoặc gửi phản hồi. Thay vào đó, chúng ta có thể stream một phản hồi khi công việc hoàn tất.

> **React Server Component Payload là gì?**
>
> React Server Component Payload là một biểu diễn nhị phân nhỏ gọn của React Server Components tree đã được render. Nó được sử dụng bởi React trên client để cập nhật DOM của trình duyệt. React Server Component Payload chứa:
>
> - Kết quả đã render của Server Components
> - Các placeholder cho nơi Client Components sẽ được render và tham chiếu đến các tệp JavaScript của chúng
> - Bất kỳ props nào được truyền từ một Server Component đến một Client Component
>
> Để tìm hiểu thêm, xem tài liệu [Server Components](/docs/app/getting-started/server-and-client-components).

Hành vi mặc định của Next.js là cache kết quả đã render (React Server Component Payload và HTML) của một route trên server. Điều này áp dụng cho các routes được render tĩnh tại build time, hoặc trong quá trình revalidation.

### 3. React Hydration và Reconciliation trên Client

Tại request time, trên client:

1. HTML được sử dụng để hiển thị ngay lập tức bản xem trước ban đầu không tương tác nhanh của Client và Server Components.
2. React Server Components Payload được sử dụng để đối chiếu Client và Server Component trees đã render, và cập nhật DOM.
3. Các hướng dẫn JavaScript được sử dụng để [hydrate](https://react.dev/reference/react-dom/client/hydrateRoot) Client Components và làm cho ứng dụng tương tác.

### 4. Next.js Caching trên Client (Router Cache)

React Server Component Payload được lưu trữ trong client-side [Router Cache](#client-side-router-cache) - một bộ nhớ cache trong bộ nhớ riêng biệt, được chia theo từng phân đoạn route riêng lẻ. Router Cache này được sử dụng để cải thiện trải nghiệm điều hướng bằng cách lưu trữ các routes đã truy cập trước đó và prefetching các routes trong tương lai.

### 5. Các điều hướng tiếp theo

Trên các điều hướng tiếp theo hoặc trong quá trình prefetching, Next.js sẽ kiểm tra xem React Server Components Payload có được lưu trữ trong Router Cache hay không. Nếu có, nó sẽ bỏ qua việc gửi yêu cầu mới đến server.

Nếu các phân đoạn route không có trong cache, Next.js sẽ fetch React Server Components Payload từ server, và điền vào Router Cache trên client.

### Static và Dynamic Rendering

Việc một route có được cache hay không tại build time phụ thuộc vào việc nó được render tĩnh hay động. Static routes được cache theo mặc định, trong khi dynamic routes được render tại request time, và không được cache.

Sơ đồ này hiển thị sự khác biệt giữa các routes được render tĩnh và động, với dữ liệu được cache và không được cache:

### Thời lượng

Theo mặc định, Full Route Cache là bền vững. Điều này có nghĩa là đầu ra render được cache qua các yêu cầu người dùng.

### Invalidation

Có hai cách bạn có thể invalidate Full Route Cache:

- **[Revalidating Data](/docs/app/guides/caching#revalidating)**: Revalidating [Data Cache](#data-cache), sẽ lần lượt invalidate Router Cache bằng cách render lại các components trên server và cache đầu ra render mới.
- **Redeploying**: Không giống như Data Cache, tồn tại qua các lần triển khai, Full Route Cache bị xóa khi triển khai mới.

### Opting out

Bạn có thể chọn không tham gia (opt out) Full Route Cache, hay nói cách khác, render động các components cho mỗi yêu cầu đến, bằng cách:

- **Sử dụng một [Dynamic API](#dynamic-apis)**: Điều này sẽ opt route ra khỏi Full Route Cache và render động nó tại request time. Data Cache vẫn có thể được sử dụng.
- **Sử dụng các tùy chọn cấu hình phân đoạn route `dynamic = 'force-dynamic'` hoặc `revalidate = 0`**: Điều này sẽ bỏ qua Full Route Cache và Data Cache. Có nghĩa là các components sẽ được render và dữ liệu được fetch trên mỗi yêu cầu đến server. Router Cache vẫn sẽ áp dụng vì nó là một cache phía client.
- **Opting out của [Data Cache](#data-cache)**: Nếu một route có một yêu cầu `fetch` không được cache, điều này sẽ opt route ra khỏi Full Route Cache. Dữ liệu cho yêu cầu `fetch` cụ thể sẽ được fetch cho mỗi yêu cầu đến. Các yêu cầu `fetch` khác cho phép caching một cách rõ ràng vẫn sẽ được cache trong Data Cache. Điều này cho phép kết hợp dữ liệu được cache và không được cache.

## Client-side Router Cache

Next.js có một bộ nhớ cache router phía client trong bộ nhớ lưu trữ RSC payload của các phân đoạn route, được chia theo layouts, loading states, và pages.

Khi người dùng điều hướng giữa các routes, Next.js cache các phân đoạn route đã truy cập và [prefetches](/docs/app/getting-started/linking-and-navigating#prefetching) các routes mà người dùng có khả năng điều hướng đến. Điều này dẫn đến điều hướng quay lại/tiến lên ngay lập tức, không tải lại toàn bộ trang giữa các điều hướng, và bảo tồn trạng thái trình duyệt và trạng thái React trong các layouts được chia sẻ.

Với Router Cache:

- **Layouts** được cache và tái sử dụng khi điều hướng ([partial rendering](/docs/app/getting-started/linking-and-navigating#client-side-transitions)).
- **Loading states** được cache và tái sử dụng khi điều hướng cho [instant navigation](/docs/app/api-reference/file-conventions/loading#instant-loading-states).
- **Pages** không được cache theo mặc định, nhưng được tái sử dụng trong quá trình điều hướng quay lại và tiến lên của trình duyệt. Bạn có thể bật caching cho các phân đoạn page bằng cách sử dụng tùy chọn cấu hình thử nghiệm [`staleTimes`](/docs/app/api-reference/config/next-config-js/staleTimes).

> **Thông tin hữu ích:** Cache này áp dụng cụ thể cho Next.js và Server Components, và khác với [bfcache](https://web.dev/bfcache/) của trình duyệt, mặc dù nó có kết quả tương tự.

### Thời lượng

Cache được lưu trữ trong bộ nhớ tạm thời của trình duyệt. Hai yếu tố xác định thời gian tồn tại của router cache:

- **Phiên (Session)**: Cache tồn tại qua điều hướng. Tuy nhiên, nó bị xóa khi refresh trang.
- **Thời gian Invalidation Tự động**: Cache của layouts và loading states được tự động invalidate sau một thời gian cụ thể. Thời lượng phụ thuộc vào cách tài nguyên được [prefetched](/docs/app/api-reference/components/link#prefetch), và liệu tài nguyên có được [tạo tĩnh](#static-rendering) hay không:
  - **Default Prefetching** (`prefetch={null}` hoặc không xác định): không được cache cho dynamic pages, 5 phút cho static pages.
  - **Full Prefetching** (`prefetch={true}` hoặc `router.prefetch`): 5 phút cho cả static & dynamic pages.

Trong khi refresh trang sẽ xóa **tất cả** các phân đoạn đã được cache, thời gian invalidation tự động chỉ ảnh hưởng đến phân đoạn riêng lẻ từ thời điểm nó được prefetched.

> **Thông tin hữu ích**: Tùy chọn cấu hình thử nghiệm [`staleTimes`](/docs/app/api-reference/config/next-config-js/staleTimes) có thể được sử dụng để điều chỉnh thời gian invalidation tự động được đề cập ở trên.

### Invalidation

Có hai cách bạn có thể invalidate Router Cache:

- Trong một **Server Action**:
  - Revalidating dữ liệu theo yêu cầu theo path với ([`revalidatePath`](/docs/app/api-reference/functions/revalidatePath)) hoặc theo cache tag với ([`revalidateTag`](/docs/app/api-reference/functions/revalidateTag))
  - Sử dụng [`cookies.set`](/docs/app/api-reference/functions/cookies#setting-a-cookie) hoặc [`cookies.delete`](/docs/app/api-reference/functions/cookies#deleting-cookies) invalidates Router Cache để ngăn các routes sử dụng cookies trở nên cũ (ví dụ: xác thực).
- Gọi [`router.refresh`](/docs/app/api-reference/functions/use-router) sẽ invalidate Router Cache và thực hiện một yêu cầu mới đến server cho route hiện tại.

### Opting out

Kể từ Next.js 15, các phân đoạn page được chọn không tham gia (opted out) theo mặc định.

> **Thông tin hữu ích:** Bạn cũng có thể chọn không tham gia [prefetching](/docs/app/getting-started/linking-and-navigating#prefetching) bằng cách đặt prop `prefetch` của component `<Link>` thành `false`.

## Tương tác Cache

Khi định cấu hình các cơ chế caching khác nhau, điều quan trọng là phải hiểu cách chúng tương tác với nhau:

### Data Cache và Full Route Cache

- Revalidating hoặc opting out của Data Cache **sẽ** invalidate Full Route Cache, vì đầu ra render phụ thuộc vào dữ liệu.
- Invalidating hoặc opting out của Full Route Cache **không** ảnh hưởng đến Data Cache. Bạn có thể render động một route có cả dữ liệu được cache và không được cache. Điều này hữu ích khi hầu hết trang của bạn sử dụng dữ liệu được cache, nhưng bạn có một vài components dựa vào dữ liệu cần được fetch tại request time. Bạn có thể render động mà không phải lo lắng về tác động hiệu suất của việc fetch lại tất cả dữ liệu.

### Data Cache và Client-side Router cache

- Để invalidate ngay lập tức Data Cache và Router cache, bạn có thể sử dụng [`revalidatePath`](#revalidatepath) hoặc [`revalidateTag`](#fetch-optionsnexttags-and-revalidatetag) trong một [Server Action](/docs/app/getting-started/updating-data).
- Revalidating Data Cache trong một [Route Handler](/docs/app/api-reference/file-conventions/route) **sẽ không** invalidate ngay lập tức Router Cache vì Route Handler không gắn liền với một route cụ thể. Điều này có nghĩa là Router Cache sẽ tiếp tục phục vụ payload trước đó cho đến khi hard refresh, hoặc thời gian invalidation tự động đã trôi qua.

### `<Link>`

Theo mặc định, component `<Link>` tự động prefetches các routes từ Full Route Cache và thêm React Server Component Payload vào Router Cache.

Để tắt prefetching, bạn có thể đặt prop `prefetch` thành `false`. Nhưng điều này sẽ không bỏ qua cache vĩnh viễn, phân đoạn route vẫn sẽ được cache phía client khi người dùng truy cập route.

Tìm hiểu thêm về [`<Link>` component](/docs/app/api-reference/components/link).

### `router.prefetch`

Tùy chọn `prefetch` của hook `useRouter` có thể được sử dụng để prefetch thủ công một route. Điều này thêm React Server Component Payload vào Router Cache.

Xem tham chiếu API [`useRouter` hook](/docs/app/api-reference/functions/use-router).

### `router.refresh`

Tùy chọn `refresh` của hook `useRouter` có thể được sử dụng để refresh thủ công một route. Điều này xóa hoàn toàn Router Cache, và thực hiện một yêu cầu mới đến server cho route hiện tại. `refresh` không ảnh hưởng đến Data hoặc Full Route Cache.

Kết quả đã render sẽ được đối chiếu trên client trong khi bảo tồn trạng thái React và trạng thái trình duyệt.

Xem tham chiếu API [`useRouter` hook](/docs/app/api-reference/functions/use-router).

### `fetch`

Dữ liệu trả về từ `fetch` _không_ được tự động cache trong Data Cache.

Theo mặc định, khi không có tùy chọn `cache` hoặc `next.revalidate` nào được cung cấp:

- [Dynamic rendering](#dynamic-rendering): Fetch chạy trên mỗi yêu cầu và luôn trả về dữ liệu mới.
- [Static rendering](#static-rendering): Dữ liệu đã fetch được lưu trữ trong [Data Cache](#data-cache), và đầu ra đã render trong [Full Route Cache](#full-route-cache). Next.js phục vụ kết quả đã cache này cho đến khi đường dẫn được revalidate.

Xem [`fetch` API Reference](/docs/app/api-reference/functions/fetch) để biết thêm các tùy chọn.

### `fetch options.cache`

Bạn có thể chọn tham gia caching cho `fetch` riêng lẻ bằng cách đặt tùy chọn `cache` thành `force-cache`:

```jsx
// Opt into caching
fetch(`https://...`, { cache: 'force-cache' })
```

Xem [`fetch` API Reference](/docs/app/api-reference/functions/fetch) để biết thêm các tùy chọn.

### `fetch options.next.revalidate`

Bạn có thể sử dụng tùy chọn `next.revalidate` của `fetch` để đặt thời gian revalidation (tính bằng giây) của một yêu cầu `fetch` riêng lẻ. Điều này sẽ revalidate Data Cache, từ đó sẽ revalidate Full Route Cache. Dữ liệu mới sẽ được fetch, và các components sẽ được render lại trên server.

```jsx
// Revalidate at most after 1 hour
fetch(`https://...`, { next: { revalidate: 3600 } })
```

Xem [`fetch` API reference](/docs/app/api-reference/functions/fetch) để biết thêm các tùy chọn.

### `fetch options.next.tags` và `revalidateTag`

Next.js có một hệ thống gắn thẻ cache cho việc caching và revalidation dữ liệu chi tiết.

1. Khi sử dụng `fetch` hoặc [`unstable_cache`](/docs/app/api-reference/functions/unstable_cache), bạn có tùy chọn gắn thẻ các mục cache với một hoặc nhiều tags.
2. Sau đó, bạn có thể gọi `revalidateTag` để xóa các mục cache được liên kết với tag đó.

Ví dụ, bạn có thể đặt một tag khi fetching dữ liệu:

```jsx
// Cache data with a tag
fetch(`https://...`, { next: { tags: ['a', 'b', 'c'] } })
```

Sau đó, gọi `revalidateTag` với một tag để xóa mục cache:

```jsx
// Revalidate entries with a specific tag
revalidateTag('a')
```

Có hai nơi bạn có thể sử dụng `revalidateTag`, tùy thuộc vào những gì bạn đang cố gắng đạt được:

1. [Route Handlers](/docs/app/api-reference/file-conventions/route) - để revalidate dữ liệu trong phản hồi của một sự kiện bên thứ ba (ví dụ: webhook). Điều này sẽ không invalidate Router Cache ngay lập tức vì Router Handler không gắn liền với một route cụ thể.
2. [Server Actions](/docs/app/getting-started/updating-data) - để revalidate dữ liệu sau một hành động của người dùng (ví dụ: gửi biểu mẫu). Điều này sẽ invalidate Router Cache cho route được liên kết.

### `revalidatePath`

`revalidatePath` cho phép bạn revalidate thủ công dữ liệu **và** render lại các phân đoạn route bên dưới một đường dẫn cụ thể trong một thao tác duy nhất. Gọi phương thức `revalidatePath` revalidates Data Cache, từ đó invalidates Full Route Cache.

```jsx
revalidatePath('/')
```

Có hai nơi bạn có thể sử dụng `revalidatePath`, tùy thuộc vào những gì bạn đang cố gắng đạt được:

1. [Route Handlers](/docs/app/api-reference/file-conventions/route) - để revalidate dữ liệu trong phản hồi của một sự kiện bên thứ ba (ví dụ: webhook).
2. [Server Actions](/docs/app/getting-started/updating-data) - để revalidate dữ liệu sau một tương tác của người dùng (ví dụ: gửi biểu mẫu, nhấp vào nút).

Xem [`revalidatePath` API reference](/docs/app/api-reference/functions/revalidatePath) để biết thêm thông tin.

> **`revalidatePath`** so với **`router.refresh`**:
>
> Gọi `router.refresh` sẽ xóa Router cache, và render lại các phân đoạn route trên server mà không invalidate Data Cache hoặc Full Route Cache.
>
> Sự khác biệt là `revalidatePath` xóa Data Cache và Full Route Cache, trong khi `router.refresh()` không thay đổi Data Cache và Full Route Cache, vì nó là một API phía client.

### Dynamic APIs

Dynamic APIs như `cookies` và `headers`, và prop `searchParams` trong Pages phụ thuộc vào thông tin yêu cầu đến tại runtime. Sử dụng chúng sẽ opt một route ra khỏi Full Route Cache, nói cách khác, route sẽ được render động.

#### `cookies`

Sử dụng `cookies.set` hoặc `cookies.delete` trong một Server Action invalidates Router Cache để ngăn các routes sử dụng cookies trở nên cũ (ví dụ: để phản ánh các thay đổi xác thực).

Xem [`cookies`](/docs/app/api-reference/functions/cookies) API reference.

### Tùy chọn cấu hình phân đoạn

Các tùy chọn Route Segment Config có thể được sử dụng để ghi đè các giá trị mặc định của phân đoạn route hoặc khi bạn không thể sử dụng `fetch` API (ví dụ: database client hoặc thư viện bên thứ 3).

Các tùy chọn Route Segment Config sau đây sẽ opt out của Full Route Cache:

- `const dynamic = 'force-dynamic'`

Tùy chọn cấu hình này sẽ opt tất cả các fetches ra khỏi Data Cache (tức là `no-store`):

- `const fetchCache = 'default-no-store'`

Xem [`fetchCache`](/docs/app/api-reference/file-conventions/route-segment-config#fetchcache) để xem thêm các tùy chọn nâng cao.

Xem tài liệu [Route Segment Config](/docs/app/api-reference/file-conventions/route-segment-config) để biết thêm các tùy chọn.

### `generateStaticParams`

Đối với [dynamic segments](/docs/app/api-reference/file-conventions/dynamic-routes) (ví dụ: `app/blog/[slug]/page.js`), các đường dẫn được cung cấp bởi `generateStaticParams` được cache trong Full Route Cache tại build time. Tại request time, Next.js cũng sẽ cache các đường dẫn không được biết đến tại build time lần đầu tiên chúng được truy cập.

Để render tĩnh tất cả các đường dẫn tại build time, cung cấp danh sách đầy đủ các đường dẫn cho `generateStaticParams`:

```jsx filename="app/blog/[slug]/page.js"
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())

  return posts.map((post) => ({
    slug: post.slug,
  }))
}
```

Để render tĩnh một tập hợp con các đường dẫn tại build time, và phần còn lại lần đầu tiên chúng được truy cập tại runtime, trả về một danh sách một phần các đường dẫn:

```jsx filename="app/blog/[slug]/page.js"
export async function generateStaticParams() {
  const posts = await fetch('https://.../posts').then((res) => res.json())

  // Render the first 10 posts at build time
  return posts.slice(0, 10).map((post) => ({
    slug: post.slug,
  }))
}
```

Để render tĩnh tất cả các đường dẫn lần đầu tiên chúng được truy cập, trả về một mảng trống (không có đường dẫn nào sẽ được render tại build time) hoặc sử dụng [`export const dynamic = 'force-static'`](/docs/app/api-reference/file-conventions/route-segment-config#dynamic):

```jsx filename="app/blog/[slug]/page.js"
export async function generateStaticParams() {
  return []
}
```

> **Thông tin hữu ích:** Bạn phải trả về một mảng từ `generateStaticParams`, ngay cả khi nó trống. Nếu không, route sẽ được render động.

```jsx filename="app/changelog/[slug]/page.js"
export const dynamic = 'force-static'
```

Để tắt caching tại request time, thêm tùy chọn `export const dynamicParams = false` trong một phân đoạn route. Khi tùy chọn cấu hình này được sử dụng, chỉ các đường dẫn được cung cấp bởi `generateStaticParams` sẽ được phục vụ, và các routes khác sẽ 404 hoặc khớp (trong trường hợp [catch-all routes](/docs/app/api-reference/file-conventions/dynamic-routes#catch-all-segments)).

### Hàm React `cache`

Hàm React `cache` cho phép bạn memoize giá trị trả về của một hàm, cho phép bạn gọi cùng một hàm nhiều lần trong khi chỉ thực thi nó một lần.

Các yêu cầu `fetch` sử dụng các phương thức `GET` hoặc `HEAD` được tự động memoized, vì vậy bạn không cần bọc nó trong React `cache`. Tuy nhiên, đối với các phương thức `fetch` khác, hoặc khi sử dụng các thư viện fetching dữ liệu (chẳng hạn như một số database, CMS, hoặc GraphQL clients) không vốn có memoize các yêu cầu, bạn có thể sử dụng `cache` để memoize thủ công các yêu cầu dữ liệu.

```ts filename="utils/get-item.ts" switcher
import { cache } from 'react'
import db from '@/lib/db'

export const getItem = cache(async (id: string) => {
  const item = await db.item.findUnique({ id })
  return item
})
```

```js filename="utils/get-item.js" switcher
import { cache } from 'react'
import db from '@/lib/db'

export const getItem = cache(async (id) => {
  const item = await db.item.findUnique({ id })
  return item
})
```
