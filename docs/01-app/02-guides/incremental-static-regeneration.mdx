Incremental Static Regeneration (ISR) cho phép bạn:

- Cập nhật nội dung tĩnh mà không cần build lại toàn bộ trang web
- Giảm tải máy chủ bằng cách phục vụ các trang tĩnh, được render trước cho hầu hết các yêu cầu
- Đảm bảo các header `cache-control` phù hợp được tự động thêm vào các trang
- Xử lý lượng lớn các trang nội dung mà không mất nhiều thời gian `next build`

Dưới đây là một ví dụ tối thiểu:

<AppOnly>

```tsx filename="app/blog/[id]/page.tsx" switcher
interface Post {
  id: string
  title: string
  content: string
}

// Next.js sẽ làm mất hiệu lực bộ nhớ cache khi một
// yêu cầu đến, tối đa một lần mỗi 60 giây.
export const revalidate = 60

export async function generateStaticParams() {
  const posts: Post[] = await fetch('https://api.vercel.app/blog').then((res) =>
    res.json()
  )
  return posts.map((post) => ({
    id: String(post.id),
  }))
}

export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const post: Post = await fetch(`https://api.vercel.app/blog/${id}`).then(
    (res) => res.json()
  )
  return (
    <main>
      <h1>{post.title}</h1>
      <p>{post.content}</p>
    </main>
  )
}
```

Dưới đây là cách ví dụ này hoạt động:

1. Trong quá trình `next build`, tất cả các bài đăng blog đã biết được tạo ra
2. Tất cả các yêu cầu được thực hiện đến các trang này (ví dụ `/blog/1`) được lưu trong bộ nhớ cache và tức thời
3. Sau khi 60 giây trôi qua, yêu cầu tiếp theo vẫn sẽ trả về trang đã lưu trong bộ nhớ cache (bây giờ đã cũ)
4. Bộ nhớ cache bị mất hiệu lực và một phiên bản mới của trang bắt đầu tạo trong nền
5. Sau khi tạo thành công, yêu cầu tiếp theo sẽ trả về trang đã cập nhật và lưu vào bộ nhớ cache cho các yêu cầu tiếp theo
6. Nếu `/blog/26` được yêu cầu, và nó tồn tại, trang sẽ được tạo theo yêu cầu (on-demand). Hành vi này có thể được thay đổi bằng cách sử dụng một giá trị [dynamicParams](/docs/app/api-reference/file-conventions/route-segment-config#dynamicparams) khác. Tuy nhiên, nếu bài đăng không tồn tại, thì 404 được trả về.

### Xác thực lại dựa trên thời gian (Time-based revalidation)

Điều này tìm nạp và hiển thị danh sách các bài đăng blog trên /blog. Sau khi một giờ trôi qua, khách truy cập tiếp theo vẫn sẽ nhận được phiên bản đã lưu trong bộ nhớ cache (cũ) của trang ngay lập tức để có phản hồi nhanh. Đồng thời, Next.js kích hoạt việc tạo lại một phiên bản mới trong nền. Sau khi phiên bản mới được tạo thành công, nó sẽ thay thế phiên bản đã lưu trong bộ nhớ cache, và những khách truy cập tiếp theo sẽ nhận được nội dung cập nhật.

```tsx filename="app/blog/page.tsx" switcher
interface Post {
  id: string
  title: string
  content: string
}

export const revalidate = 3600 // làm mất hiệu lực mỗi giờ

export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog')
  const posts: Post[] = await data.json()
  return (
    <main>
      <h1>Blog Posts</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>{post.title}</li>
        ))}
      </ul>
    </main>
  )
}
```

```jsx filename="app/blog/page.js" switcher
export const revalidate = 3600 // làm mất hiệu lực mỗi giờ

export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog')
  const posts = await data.json()
  return (
    <main>
      <h1>Blog Posts</h1>
      <ul>
        {posts.map((post) => (
          <li key={post.id}>{post.title}</li>
        ))}
      </ul>
    </main>
  )
}
```

Chúng tôi khuyên bạn nên đặt thời gian xác thực lại cao. Ví dụ, 1 giờ thay vì 1 giây. Nếu bạn cần độ chính xác cao hơn, hãy xem xét sử dụng xác thực lại theo yêu cầu (on-demand revalidation). Nếu bạn cần dữ liệu thời gian thực, hãy xem xét chuyển sang [render động](/docs/app/guides/caching#dynamic-rendering).

### Xác thực lại theo yêu cầu với `revalidatePath`

Để có phương pháp xác thực lại chính xác hơn, hãy làm mất hiệu lực các trang đã lưu trong bộ nhớ cache theo yêu cầu với hàm `revalidatePath`.

Ví dụ, Server Action này sẽ được gọi sau khi thêm một bài đăng mới. Bất kể bạn truy xuất dữ liệu của mình trong Server Component như thế nào, sử dụng `fetch` hoặc kết nối với cơ sở dữ liệu, điều này sẽ làm mất hiệu lực bộ nhớ cache cho toàn bộ route. Yêu cầu tiếp theo đến route đó sẽ kích hoạt việc tạo lại và phục vụ dữ liệu mới, sau đó sẽ được lưu vào bộ nhớ cache cho các yêu cầu tiếp theo.

> **Lưu ý:** `revalidatePath` làm mất hiệu lực các mục nhập bộ nhớ cache nhưng việc tạo lại xảy ra vào yêu cầu tiếp theo. Nếu bạn muốn tạo lại mục nhập bộ nhớ cache ngay lập tức thay vì chờ yêu cầu tiếp theo, bạn có thể sử dụng phương thức [`res.revalidate`](docs/pages/guides/incremental-static-regeneration#on-demand-validation-with-resrevalidate) của Pages router. Chúng tôi đang làm việc để thêm các phương thức mới để cung cấp khả năng tạo lại ngay lập tức cho App Router.

```ts filename="app/actions.ts" switcher
'use server'

import { revalidatePath } from 'next/cache'

export async function createPost() {
  // Làm mất hiệu lực bộ nhớ cache cho route /posts
  revalidatePath('/posts')
}
```

```js filename="app/actions.js" switcher
'use server'

import { revalidatePath } from 'next/cache'

export async function createPost() {
  // Làm mất hiệu lực bộ nhớ cache cho route /posts
  revalidatePath('/posts')
}
```

[Xem demo](https://on-demand-isr.vercel.app) và [khám phá mã nguồn](https://github.com/vercel/on-demand-isr).

### Xác thực lại theo yêu cầu với `revalidateTag`

Đối với hầu hết các trường hợp sử dụng, hãy ưu tiên xác thực lại toàn bộ đường dẫn. Nếu bạn cần kiểm soát chi tiết hơn, bạn có thể sử dụng hàm `revalidateTag`. Ví dụ, bạn có thể gắn thẻ các lệnh gọi `fetch` riêng lẻ:

```tsx filename="app/blog/page.tsx" switcher
export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog', {
    next: { tags: ['posts'] },
  })
  const posts = await data.json()
  // ...
}
```

```jsx filename="app/blog/page.js" switcher
export default async function Page() {
  const data = await fetch('https://api.vercel.app/blog', {
    next: { tags: ['posts'] },
  })
  const posts = await data.json()
  // ...
}
```

Nếu bạn đang sử dụng ORM hoặc kết nối với cơ sở dữ liệu, bạn có thể sử dụng `unstable_cache`:

```tsx filename="app/blog/page.tsx" switcher
import { unstable_cache } from 'next/cache'
import { db, posts } from '@/lib/db'

const getCachedPosts = unstable_cache(
  async () => {
    return await db.select().from(posts)
  },
  ['posts'],
  { revalidate: 3600, tags: ['posts'] }
)

export default async function Page() {
  const posts = getCachedPosts()
  // ...
}
```

```jsx filename="app/blog/page.js" switcher
import { unstable_cache } from 'next/cache'
import { db, posts } from '@/lib/db'

const getCachedPosts = unstable_cache(
  async () => {
    return await db.select().from(posts)
  },
  ['posts'],
  { revalidate: 3600, tags: ['posts'] }
)

export default async function Page() {
  const posts = getCachedPosts()
  // ...
}
```

```ts filename="app/actions.ts" switcher
  revalidateTag('posts')

```

### Xác thực theo yêu cầu với `res.revalidate()`

Để có phương pháp xác thực lại chính xác hơn, hãy sử dụng `res.revalidate` để tạo một trang mới theo yêu cầu từ API Router.

Ví dụ, API Route này có thể được gọi tại `/api/revalidate?secret=<token>` để xác thực lại một bài đăng blog nhất định. Tạo một token bí mật chỉ được biết bởi ứng dụng Next.js của bạn. Bí mật này sẽ được sử dụng để ngăn chặn truy cập trái phép vào API Route xác thực lại.

```ts filename="pages/api/revalidate.ts" switcher
import type { NextApiRequest, NextApiResponse } from 'next'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  // Kiểm tra bí mật để xác nhận đây là yêu cầu hợp lệ
  if (req.query.secret !== process.env.MY_SECRET_TOKEN) {
    return res.status(401).json({ message: 'Invalid token' })
  }

  try {
    // Đây phải là đường dẫn thực tế không phải là đường dẫn được viết lại
    // ví dụ: đối với "/posts/[id]" đây phải là "/posts/1"
    await res.revalidate('/posts/1')
    return res.json({ revalidated: true })
  } catch (err) {
    // Nếu có lỗi, Next.js sẽ tiếp tục
    // hiển thị trang được tạo thành công cuối cùng
    return res.status(500).send('Error revalidating')
  }
}
```

### Xử lý các ngoại lệ không được bắt (uncaught exceptions)

<AppOnly>

Nếu một lỗi được ném ra trong khi cố gắng xác thực lại dữ liệu, dữ liệu được tạo thành công cuối cùng sẽ tiếp tục được phục vụ từ bộ nhớ cache. Trong yêu cầu tiếp theo, Next.js sẽ thử lại việc xác thực lại dữ liệu. [Tìm hiểu thêm về xử lý lỗi](/docs/app/getting-started/error-handling).

</AppOnly>

<PagesOnly>

Nếu có lỗi bên trong `getStaticProps` khi xử lý việc tạo lại trong nền, hoặc bạn ném lỗi thủ công, trang được tạo thành công cuối cùng sẽ tiếp tục hiển thị. Trong yêu cầu tiếp theo, Next.js sẽ thử lại việc gọi `getStaticProps`.

```tsx filename="pages/blog/[id].tsx" switcher
import type { GetStaticProps } from 'next'

interface Post {
  id: string
  title: string
  content: string
}

interface Props {
  post: Post
}

export const getStaticProps: GetStaticProps<Props> = async ({
  params,
}: {
  params: { id: string }
}) => {
  // Nếu yêu cầu này ném ra lỗi không được bắt, Next.js sẽ
  // không làm mất hiệu lực trang đang hiển thị và
  // thử lại getStaticProps vào yêu cầu tiếp theo.
  const res = await fetch(`https://api.vercel.app/blog/${params.id}`)
  const post: Post = await res.json()

  if (!res.ok) {
    // Nếu có lỗi máy chủ, bạn có thể muốn
    // ném lỗi thay vì trả về để bộ nhớ cache không được cập nhật
    // cho đến yêu cầu thành công tiếp theo.
    throw new Error(`Failed to fetch posts, received status ${res.status}`)
  }

  return {
    props: { post },
    // Next.js sẽ làm mất hiệu lực bộ nhớ cache khi một
    // yêu cầu đến, tối đa một lần mỗi 60 giây.
    revalidate: 60,
  }
}
```

```jsx filename="pages/blog/[id].jsx" switcher
    // Next.js sẽ làm mất hiệu lực bộ nhớ cache khi một
    // yêu cầu đến, tối đa một lần mỗi 60 giây.
    revalidate: 60,
  }
}
```

</PagesOnly>

### Tùy chỉnh vị trí bộ nhớ cache

Bạn có thể cấu hình vị trí bộ nhớ cache Next.js nếu bạn muốn duy trì các trang và dữ liệu đã lưu trong bộ nhớ cache vào bộ nhớ bền vững, hoặc chia sẻ bộ nhớ cache qua nhiều container hoặc instance của ứng dụng Next.js của bạn. [Tìm hiểu thêm](/docs/app/guides/self-hosting#caching-and-isr).

## Khắc phục sự cố

### Gỡ lỗi dữ liệu đã lưu trong bộ nhớ cache trong phát triển cục bộ

Nếu bạn đang sử dụng API `fetch`, bạn có thể thêm logging bổ sung để hiểu yêu cầu nào được lưu trong bộ nhớ cache hoặc không được lưu. [Tìm hiểu thêm về tùy chọn `logging`](/docs/app/api-reference/config/next-config-js/logging).

```jsx filename="next.config.js"
module.exports = {
  logging: {
    fetches: {
      fullUrl: true,
    },
  },
}
```

### Xác minh hành vi production chính xác

Để xác minh các trang của bạn được lưu trong bộ nhớ cache và xác thực lại chính xác trong production, bạn có thể kiểm tra cục bộ bằng cách chạy `next build` và sau đó `next start` để chạy máy chủ Next.js production.

Điều này sẽ cho phép bạn kiểm tra hành vi ISR như nó sẽ hoạt động trong môi trường production. Để gỡ lỗi thêm, hãy thêm biến môi trường sau vào tệp `.env` của bạn:

```bash filename=".env"
NEXT_PRIVATE_DEBUG_CACHE=1
```

Điều này sẽ làm cho console máy chủ Next.js ghi lại các lần truy cập và bỏ lỡ bộ nhớ cache ISR. Bạn có thể kiểm tra đầu ra để xem trang nào được tạo trong quá trình `next build`, cũng như cách các trang được cập nhật khi các đường dẫn được truy cập theo yêu cầu.

## Lưu ý

<AppOnly>

- ISR chỉ được hỗ trợ khi sử dụng Node.js runtime (mặc định).
- ISR không được hỗ trợ khi tạo [Static Export](/docs/app/guides/static-exports).
- Nếu bạn có nhiều yêu cầu `fetch` trong một route được render tĩnh, và mỗi yêu cầu có tần suất `revalidate` khác nhau, thời gian thấp nhất sẽ được sử dụng cho ISR. Tuy nhiên, các tần suất xác thực lại đó vẫn sẽ được tôn trọng bởi [Data Cache](/docs/app/guides/caching#data-cache).
- Nếu bất kỳ yêu cầu `fetch` nào được sử dụng trên một route có thời gian `revalidate` là `0`, hoặc `no-store` rõ ràng, route sẽ được [render động](/docs/app/guides/caching#dynamic-rendering).
- Proxy sẽ không được thực thi cho các yêu cầu ISR theo yêu cầu, có nghĩa là bất kỳ việc viết lại đường dẫn hoặc logic nào trong Proxy sẽ không được áp dụng. Đảm bảo bạn đang xác thực lại đường dẫn chính xác. Ví dụ, `/post/1` thay vì `/post-1` đã được viết lại.
