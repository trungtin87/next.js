Khi các ứng dụng phát triển và trở nên phong phú hơn về tính năng, chúng có thể yêu cầu nhiều tài nguyên hơn khi phát triển cục bộ hoặc tạo các bản build production.

Hãy cùng khám phá một số chiến lược và kỹ thuật để tối ưu hóa bộ nhớ và giải quyết các vấn đề bộ nhớ phổ biến trong Next.js.

## Giảm số lượng dependencies

Các ứng dụng có lượng lớn dependencies sẽ sử dụng nhiều bộ nhớ hơn.

[Bundle Analyzer](/docs/app/guides/package-bundling) có thể giúp bạn điều tra các dependencies lớn trong ứng dụng của bạn mà có thể loại bỏ để cải thiện hiệu suất và sử dụng bộ nhớ.

## Thử `experimental.webpackMemoryOptimizations`

Bắt đầu từ `v15.0.0`, bạn có thể thêm `experimental.webpackMemoryOptimizations: true` vào tệp `next.config.js` của mình để thay đổi hành vi trong Webpack giúp giảm mức sử dụng bộ nhớ tối đa nhưng có thể tăng thời gian biên dịch lên một chút.

> **Cần biết**: Tính năng này hiện đang thử nghiệm để kiểm tra trên nhiều dự án hơn trước, nhưng nó được coi là rủi ro thấp.

## Chạy `next build` với `--experimental-debug-memory-usage`

Bắt đầu từ `14.2.0`, bạn có thể chạy `next build --experimental-debug-memory-usage` để chạy bản build ở chế độ mà Next.js sẽ in ra thông tin về việc sử dụng bộ nhớ liên tục trong suốt quá trình build, chẳng hạn như mức sử dụng heap và thống kê garbage collection. Heap snapshots cũng sẽ được chụp tự động khi mức sử dụng bộ nhớ gần đạt đến giới hạn đã cấu hình.

> **Cần biết**: Tính năng này không tương thích với tùy chọn Webpack build worker, tùy chọn này được tự động bật trừ khi bạn có cấu hình webpack tùy chỉnh.

## Ghi lại heap profile

Để tìm kiếm các vấn đề về bộ nhớ, bạn có thể ghi lại heap profile từ Node.js và tải nó trong Chrome DevTools để xác định các nguồn rò rỉ bộ nhớ tiềm ẩn.

Trong terminal của bạn, truyền cờ `--heap-prof` cho Node.js khi bắt đầu build Next.js của bạn:

```sh
node --heap-prof node_modules/next/dist/bin/next build
```

Vào cuối quá trình build, một tệp `.heapprofile` sẽ được tạo bởi Node.js.

Trong Chrome DevTools, bạn có thể mở tab Memory và nhấp vào nút "Load Profile" để trực quan hóa tệp.

## Phân tích snapshot của heap

Bạn có thể sử dụng công cụ inspector để phân tích việc sử dụng bộ nhớ của ứng dụng.

Khi chạy lệnh `next build` hoặc `next dev`, hãy thêm `NODE_OPTIONS=--inspect` vào đầu lệnh. Điều này sẽ để lộ inspector agent trên cổng mặc định.
Nếu bạn muốn dừng trước khi bất kỳ mã người dùng nào bắt đầu, bạn có thể truyền `--inspect-brk` thay thế. Trong khi tiến trình đang chạy, bạn có thể sử dụng một công cụ như Chrome DevTools để kết nối với cổng debugging để ghi lại và phân tích snapshot của heap để xem bộ nhớ nào đang được giữ lại.

Bắt đầu từ `14.2.0`, bạn cũng có thể chạy `next build` với cờ `--experimental-debug-memory-usage` để dễ dàng chụp heap snapshots hơn.

Trong khi chạy ở chế độ này, bạn có thể gửi tín hiệu `SIGUSR2` đến tiến trình bất cứ lúc nào, và tiến trình sẽ chụp một heap snapshot.

Heap snapshot sẽ được lưu vào thư mục gốc của dự án ứng dụng Next.js và có thể được tải trong bất kỳ trình phân tích heap nào, chẳng hạn như Chrome DevTools, để xem bộ nhớ nào được giữ lại. Chế độ này chưa tương thích với Webpack build workers.

Xem [cách ghi lại và phân tích heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots) để biết thêm thông tin.

## Webpack build worker

Webpack build worker cho phép bạn chạy các biên dịch Webpack bên trong một Node.js worker riêng biệt, điều này sẽ giảm mức sử dụng bộ nhớ của ứng dụng của bạn trong quá trình build.

Tùy chọn này được bật theo mặc định nếu ứng dụng của bạn không có cấu hình Webpack tùy chỉnh bắt đầu từ `v14.1.0`.

Nếu bạn đang sử dụng phiên bản Next.js cũ hơn hoặc bạn có cấu hình Webpack tùy chỉnh, bạn có thể bật tùy chọn này bằng cách đặt `experimental.webpackBuildWorker: true` bên trong `next.config.js` của bạn.

> **Cần biết**: Tính năng này có thể không tương thích với tất cả các plugin Webpack tùy chỉnh.

## Vô hiệu hóa Webpack cache

[Webpack cache](https://webpack.js.org/configuration/cache/) lưu các module Webpack đã tạo vào bộ nhớ và/hoặc vào đĩa để cải thiện tốc độ build. Điều này có thể
giúp ích cho hiệu suất, nhưng nó cũng sẽ làm tăng mức sử dụng bộ nhớ của ứng dụng của bạn để lưu trữ dữ liệu đã cache.

Bạn có thể vô hiệu hóa hành vi này bằng cách thêm [cấu hình Webpack tùy chỉnh](/docs/app/api-reference/config/next-config-js/webpack) vào ứng dụng của bạn:

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  webpack: (
    config,
    { buildId, dev, isServer, defaultLoaders, nextRuntime, webpack }
  ) => {
    if (config.cache && !dev) {
      config.cache = Object.freeze({
        type: 'memory',
      })
    }
    // Quan trọng: trả về config đã sửa đổi
    return config
  },
}

export default nextConfig
```

## Vô hiệu hóa phân tích tĩnh

Typechecking có thể yêu cầu nhiều bộ nhớ, đặc biệt là trong các dự án lớn.
Tuy nhiên, hầu hết các dự án đều có một CI runner chuyên dụng đã xử lý các tác vụ này.
Khi quá trình build tạo ra các vấn đề hết bộ nhớ (out-of-memory) trong bước "Running TypeScript", bạn có thể vô hiệu hóa tác vụ này trong quá trình build:

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  typescript: {
    // !! CẢNH BÁO !!
    // Nguy hiểm cho phép các bản build production hoàn thành thành công ngay cả khi
    // dự án của bạn có lỗi type.
    // !! CẢNH BÁO !!
    ignoreBuildErrors: true,
  },
}

export default nextConfig
```

- [Bỏ qua Lỗi TypeScript](/docs/app/api-reference/config/typescript#disabling-typescript-errors-in-production)

Hãy nhớ rằng điều này có thể tạo ra các bản deploy bị lỗi do lỗi type.
Chúng tôi thực sự khuyên bạn chỉ nên promote các bản build lên production sau khi phân tích tĩnh đã hoàn tất.
Nếu bạn deploy lên Vercel, bạn có thể xem [hướng dẫn cho staging deployments](https://vercel.com/docs/deployments/managing-deployments#staging-and-promoting-a-production-deployment) để tìm hiểu cách promote các bản build lên production sau khi các tác vụ tùy chỉnh đã thành công.

## Vô hiệu hóa source maps

Việc tạo source maps tiêu tốn thêm bộ nhớ trong quá trình build.

Bạn có thể vô hiệu hóa việc tạo source map bằng cách thêm `productionBrowserSourceMaps: false` và `experimental.serverSourceMaps: false` vào cấu hình Next.js của bạn.

Khi sử dụng tính năng `cacheComponents`, Next.js sẽ sử dụng source maps theo mặc định trong giai đoạn prerender của `next build`.
Nếu bạn liên tục gặp sự cố bộ nhớ trong giai đoạn đó (sau "Generating static pages"),
bạn có thể thử vô hiệu hóa source maps trong giai đoạn đó bằng cách thêm `enablePrerenderSourceMaps: false` vào cấu hình Next.js của bạn.

> **Cần biết**: Một số plugin có thể bật source maps và có thể yêu cầu cấu hình tùy chỉnh để vô hiệu hóa.

## Các vấn đề bộ nhớ Edge

Next.js `v14.1.3` đã sửa một vấn đề bộ nhớ khi sử dụng Edge runtime. Vui lòng cập nhật lên phiên bản này (hoặc mới hơn) để xem liệu nó có giải quyết được vấn đề của bạn hay không.

## Preloading Entries

Khi server Next.js khởi động, nó preloads các module JavaScript của mỗi trang vào bộ nhớ, thay vì tại thời điểm request.

Sự tối ưu hóa này cho phép thời gian phản hồi nhanh hơn, đổi lại là dung lượng bộ nhớ ban đầu lớn hơn.

Để vô hiệu hóa sự tối ưu hóa này, hãy đặt cờ `experimental.preloadEntriesOnStart` thành `false`.

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const config: NextConfig = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
```

```js filename="next.config.mjs" switcher
/** @type {import('next').NextConfig} */
const config = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
```

Next.js không unload các module JavaScript này, có nghĩa là ngay cả khi vô hiệu hóa sự tối ưu hóa này, dung lượng bộ nhớ của server Next.js của bạn cuối cùng sẽ giống nhau nếu tất cả các trang cuối cùng đều được request.
