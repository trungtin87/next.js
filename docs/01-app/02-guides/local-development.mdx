Next.js được thiết kế để cung cấp trải nghiệm tuyệt vời cho nhà phát triển. Khi ứng dụng của bạn phát triển, bạn có thể nhận thấy thời gian biên dịch chậm hơn trong quá trình phát triển cục bộ. Hướng dẫn này sẽ giúp bạn xác định và khắc phục các vấn đề hiệu suất compile-time phổ biến.

## Local dev vs. production

Quy trình phát triển với `next dev` khác với `next build` và `next start`.

`next dev` biên dịch các route trong ứng dụng của bạn khi bạn mở hoặc điều hướng đến chúng. Điều này cho phép bạn khởi động dev server mà không cần đợi mọi route trong ứng dụng của bạn biên dịch, vừa nhanh hơn vừa sử dụng ít bộ nhớ hơn. Chạy một bản build production áp dụng các tối ưu hóa khác, như minifying các tệp và tạo content hashes, những thứ không cần thiết cho phát triển cục bộ.

## Cải thiện hiệu suất local dev

### 1. Kiểm tra phần mềm diệt virus của máy tính của bạn

Phần mềm diệt virus có thể làm chậm quá trình truy cập tệp. Mặc dù điều này phổ biến hơn trên các máy Windows, nhưng đây có thể là vấn đề đối với bất kỳ hệ thống nào có cài đặt công cụ diệt virus.

Trên Windows, bạn có thể thêm dự án của mình vào [danh sách loại trừ của Microsoft Defender Antivirus](https://support.microsoft.com/en-us/windows/virus-and-threat-protection-in-the-windows-security-app-1362f4cd-d71a-b52a-0b66-c2820032b65e#bkmk_threat-protection-settings).

1. Mở ứng dụng **"Windows Security"** và sau đó chọn **"Virus & threat protection"** &rarr; **"Manage settings"** &rarr; **"Add or remove exclusions"**.
2. Thêm một loại trừ **"Folder"**. Chọn thư mục dự án của bạn.

Trên macOS, bạn có thể vô hiệu hóa [Gatekeeper](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web) bên trong terminal của bạn.

1. Chạy `sudo spctl developer-mode enable-terminal` trong terminal của bạn.
2. Mở ứng dụng **"System Settings"** và sau đó chọn **"Privacy & Security"** &rarr; **"Developer Tools"**.
3. Đảm bảo terminal của bạn được liệt kê và kích hoạt. Nếu bạn đang sử dụng terminal của bên thứ ba như iTerm hoặc Ghostty, hãy thêm nó vào danh sách.
4. Khởi động lại terminal của bạn.

### 2. Cập nhật Next.js và sử dụng Turbopack

Đảm bảo bạn đang sử dụng phiên bản mới nhất của Next.js. Mỗi phiên bản mới thường bao gồm các cải tiến về hiệu suất.

Turbopack hiện là bundler mặc định cho phát triển Next.js và cung cấp các cải tiến hiệu suất đáng kể so với webpack.

```bash
npm install next@latest
npm run dev  # Turbopack được sử dụng theo mặc định
```

Nếu bạn cần sử dụng Webpack thay vì Turbopack, bạn có thể chọn tham gia:

```bash
npm run dev --webpack
```

[Tìm hiểu thêm về Turbopack](/blog/turbopack-for-development-stable). Xem [hướng dẫn nâng cấp](/docs/app/guides/upgrading) và codemods của chúng tôi để biết thêm thông tin.

### 3. Kiểm tra các import của bạn

Cách bạn import code có thể ảnh hưởng lớn đến thời gian biên dịch và đóng gói. Tìm hiểu thêm về [tối ưu hóa đóng gói package](/docs/app/guides/package-bundling) và khám phá các công cụ như [Dependency Cruiser](https://github.com/sverweij/dependency-cruiser) hoặc [Madge](https://github.com/pahen/madge).

#### Thư viện Icon

Các thư viện như `@material-ui/icons`, `@phosphor-icons/react`, hoặc `react-icons` có thể import hàng nghìn icon, ngay cả khi bạn chỉ sử dụng một vài cái. Cố gắng chỉ import những icon bạn cần:

```jsx
// Thay vì thế này:
import { TriangleIcon } from '@phosphor-icons/react'

// Hãy làm thế này:
import { TriangleIcon } from '@phosphor-icons/react/dist/csr/Triangle'
```

Bạn thường có thể tìm thấy mẫu import nào nên sử dụng trong tài liệu cho thư viện icon bạn đang sử dụng. Ví dụ này tuân theo khuyến nghị của [`@phosphor-icons/react`](https://www.npmjs.com/package/@phosphor-icons/react#import-performance-optimization).

Các thư viện như `react-icons` bao gồm nhiều bộ icon khác nhau. Chọn một bộ và gắn bó với bộ đó.

Ví dụ, nếu ứng dụng của bạn sử dụng `react-icons` và import tất cả những thứ này:

- `pi` (Phosphor Icons)
- `md` (Material Design Icons)
- `tb` (tabler-icons)
- `cg` (cssgg)

Kết hợp lại chúng sẽ là hàng chục nghìn module mà trình biên dịch phải xử lý, ngay cả khi bạn chỉ sử dụng một import duy nhất từ mỗi cái.

#### Barrel files

"Barrel files" là các tệp export nhiều mục từ các tệp khác. Chúng có thể làm chậm quá trình build vì trình biên dịch phải phân tích cú pháp chúng để tìm xem có tác dụng phụ nào trong phạm vi module hay không bằng cách sử dụng import.

Cố gắng import trực tiếp từ các tệp cụ thể khi có thể. [Tìm hiểu thêm về barrel files](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js) và các tối ưu hóa tích hợp trong Next.js.

#### Tối ưu hóa import package

Next.js có thể tự động tối ưu hóa import cho một số package nhất định. Nếu bạn đang sử dụng các package tận dụng barrel files, hãy thêm chúng vào `next.config.js` của bạn:

```jsx
module.exports = {
  experimental: {
    optimizePackageImports: ['package-name'],
  },
}
```

Turbopack tự động phân tích các import và tối ưu hóa chúng. Nó không yêu cầu cấu hình này.

### 4. Kiểm tra thiết lập Tailwind CSS của bạn

Nếu bạn đang sử dụng Tailwind CSS, hãy đảm bảo nó được thiết lập chính xác.

Một sai lầm phổ biến là cấu hình mảng `content` của bạn theo cách bao gồm `node_modules` hoặc các thư mục lớn khác chứa các tệp không nên được quét.

Tailwind CSS phiên bản 3.4.8 hoặc mới hơn sẽ cảnh báo bạn về các cài đặt có thể làm chậm quá trình build của bạn.

1. Trong `tailwind.config.js` của bạn, hãy cụ thể về các tệp cần quét:

   ```jsx
   module.exports = {
     content: [
       './src/**/*.{js,ts,jsx,tsx}', // Tốt
       // Cái này có thể quá rộng
       // Nó sẽ khớp với `packages/**/node_modules` nữa
       // '../../packages/**/*.{js,ts,jsx,tsx}',
     ],
   }
   ```

2. Tránh quét các tệp không cần thiết:

   ```jsx
   module.exports = {
     content: [
       // Tốt hơn - chỉ quét thư mục 'src'
       '../../packages/ui/src/**/*.{js,ts,jsx,tsx}',
     ],
   }
   ```

### 5. Kiểm tra cài đặt webpack tùy chỉnh

Nếu bạn đã thêm các cài đặt webpack tùy chỉnh, chúng có thể đang làm chậm quá trình biên dịch.

Hãy xem xét liệu bạn có thực sự cần chúng cho phát triển cục bộ hay không. Bạn có thể tùy chọn chỉ bao gồm một số công cụ nhất định cho các bản build production, hoặc khám phá việc sử dụng bundler Turbopack mặc định và cấu hình [loaders](/docs/app/api-reference/config/next-config-js/turbopack#configuring-webpack-loaders) thay thế.

Nếu ứng dụng của bạn rất lớn, nó có thể cần nhiều bộ nhớ hơn.

[Tìm hiểu thêm về tối ưu hóa sử dụng bộ nhớ](/docs/app/guides/memory-usage).

### 7. Server Components và data fetching

Những thay đổi đối với Server Components khiến toàn bộ trang phải render lại cục bộ để hiển thị những thay đổi mới, bao gồm việc fetch dữ liệu mới cho component.

Tùy chọn thử nghiệm `serverComponentsHmrCache` cho phép bạn cache các phản hồi `fetch` trong Server Components qua các lần làm mới Hot Module Replacement (HMR) trong quá trình phát triển cục bộ. Điều này dẫn đến phản hồi nhanh hơn và giảm chi phí cho các cuộc gọi API bị tính phí.

[Tìm hiểu thêm về tùy chọn thử nghiệm](/docs/app/api-reference/config/next-config-js/serverComponentsHmrCache).

### 8. Cân nhắc phát triển cục bộ thay vì Docker

Nếu bạn đang sử dụng Docker để phát triển trên Mac hoặc Windows, bạn có thể gặp phải hiệu suất chậm hơn đáng kể so với chạy Next.js cục bộ.

Quyền truy cập hệ thống tệp của Docker trên Mac và Windows có thể khiến Hot Module Replacement (HMR) mất vài giây hoặc thậm chí vài phút, trong khi cùng một ứng dụng chạy với HMR nhanh khi được phát triển cục bộ.

Sự khác biệt về hiệu suất này là do cách Docker xử lý các hoạt động hệ thống tệp bên ngoài môi trường Linux. Để có trải nghiệm phát triển tốt nhất:

- Sử dụng phát triển cục bộ (`npm run dev` hoặc `pnpm dev`) thay vì Docker trong quá trình phát triển
- Dành riêng Docker cho các triển khai production và kiểm tra các bản build production
- Nếu bạn bắt buộc phải sử dụng Docker để phát triển, hãy cân nhắc sử dụng Docker trên máy Linux hoặc VM

[Tìm hiểu thêm về triển khai Docker](/docs/app/getting-started/deploying#docker) cho sử dụng production.

## Các công cụ để tìm vấn đề

### Ghi log fetch chi tiết

Sử dụng tùy chọn `logging.fetches` trong tệp `next.config.js` của bạn, để xem thông tin chi tiết hơn về những gì đang xảy ra trong quá trình phát triển:

```js
module.exports = {
  logging: {
    fetches: {
      fullUrl: true,
    },
  },
}
```

[Tìm hiểu thêm về ghi log fetch](/docs/app/api-reference/config/next-config-js/logging).

### Turbopack tracing

Turbopack tracing là một công cụ giúp bạn hiểu hiệu suất của ứng dụng trong quá trình phát triển cục bộ.
Nó cung cấp thông tin chi tiết về thời gian cần thiết để mỗi module biên dịch và cách chúng liên quan với nhau.

1. Đảm bảo bạn đã cài đặt phiên bản mới nhất của Next.js.
2. Tạo tệp trace Turbopack:

   ```bash
   NEXT_TURBOPACK_TRACING=1 npm run dev
   ```

3. Điều hướng xung quanh ứng dụng của bạn hoặc thực hiện chỉnh sửa tệp để tái tạo vấn đề.
4. Dừng development server Next.js.
5. Một tệp có tên `trace-turbopack` sẽ có sẵn trong thư mục `.next/dev`.
6. Bạn có thể diễn giải tệp bằng cách sử dụng `npx next internal trace [path-to-file]`:

   ```bash
   npx next internal trace .next/dev/trace-turbopack
   ```

   Trên các phiên bản không có sẵn `trace`, lệnh được đặt tên là `turbo-trace-server`:

   ```bash
   npx next internal turbo-trace-server .next/dev/trace-turbopack
   ```

7. Khi trace server đang chạy, bạn có thể xem trace tại https://trace.nextjs.org/.
8. Theo mặc định, trình xem trace sẽ tổng hợp thời gian, để xem từng thời gian riêng lẻ, bạn có thể chuyển từ "Aggregated in order" sang "Spans in order" ở trên cùng bên phải của trình xem.

> **Cần biết**: Tệp trace được đặt dưới thư mục development server, mặc định là `.next/dev`. Điều này có thể kiểm soát được bằng cờ [`isolatedDevBuild`](/docs/app/api-reference/config/next-config-js/isolatedDevBuild) trong tệp cấu hình Next của bạn.
