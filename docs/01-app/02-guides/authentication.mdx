Hiểu về xác thực là rất quan trọng để bảo vệ dữ liệu của ứng dụng của bạn. Trang này sẽ hướng dẫn bạn qua các tính năng React và Next.js để sử dụng nhằm triển khai xác thực.

Trước khi bắt đầu, sẽ hữu ích khi chia nhỏ quy trình thành ba khái niệm:

1. **[Xác thực (Authentication)](#authentication)**: Xác minh xem người dùng có đúng là người họ tuyên bố hay không. Nó yêu cầu người dùng chứng minh danh tính của họ bằng thứ gì đó họ có, chẳng hạn như tên người dùng và mật khẩu.
2. **[Quản lý phiên (Session Management)](#session-management)**: Theo dõi trạng thái xác thực của người dùng qua các yêu cầu.
3. **[Ủy quyền (Authorization)](#authorization)**: Quyết định những routes và dữ liệu nào người dùng có thể truy cập.

Sơ đồ này hiển thị luồng xác thực sử dụng các tính năng của React và Next.js:

Mặc dù bạn có thể triển khai giải pháp xác thực tùy chỉnh, nhưng để tăng cường bảo mật và đơn giản, chúng tôi khuyên bạn nên sử dụng thư viện xác thực. Các thư viện này cung cấp các giải pháp tích hợp cho xác thực, quản lý phiên và ủy quyền, cũng như các tính năng bổ sung như đăng nhập xã hội, xác thực đa yếu tố và kiểm soát truy cập dựa trên vai trò. Bạn có thể tìm thấy danh sách trong phần [Thư viện xác thực](#auth-libraries).

## Xác thực

<AppOnly>

### Chức năng đăng ký và đăng nhập

Bạn có thể sử dụng phần tử [`<form>`](https://react.dev/reference/react-dom/components/form) với [Server Actions](/docs/app/getting-started/updating-data) của React và `useActionState` để nắm bắt thông tin đăng nhập của người dùng, xác thực các trường biểu mẫu và gọi API hoặc cơ sở dữ liệu của Nhà cung cấp xác thực của bạn.

Vì Server Actions luôn thực thi trên server, chúng cung cấp một môi trường an toàn để xử lý logic xác thực.

Dưới đây là các bước để triển khai chức năng đăng ký/đăng nhập:

#### 1. Nắm bắt thông tin đăng nhập của người dùng

Để nắm bắt thông tin đăng nhập của người dùng, hãy tạo một biểu mẫu gọi một Server Action khi gửi. Ví dụ: một biểu mẫu đăng ký chấp nhận tên, email và mật khẩu của người dùng:

```tsx filename="app/ui/signup-form.tsx" switcher
import { signup } from '@/app/actions/auth'

export function SignupForm() {
  return (
    <form action={signup}>
      <div>
        <label htmlFor="name">Name</label>
        <input id="name" name="name" placeholder="Name" />
      </div>
      <div>
        <label htmlFor="email">Email</label>
        <input id="email" name="email" type="email" placeholder="Email" />
      </div>
      <div>
        <label htmlFor="password">Password</label>
        <input id="password" name="password" type="password" />
      </div>
      <button type="submit">Sign Up</button>
    </form>
  )
}

#### 2. Xác thực các trường biểu mẫu trên server

Sử dụng Server Action để xác thực các trường biểu mẫu trên server. Nếu nhà cung cấp xác thực của bạn không cung cấp xác thực biểu mẫu, bạn có thể sử dụng thư viện xác thực lược đồ như [Zod](https://zod.dev/) hoặc [Yup](https://github.com/jquense/yup).

Sử dụng Zod làm ví dụ, bạn có thể xác định lược đồ biểu mẫu với các thông báo lỗi thích hợp:

```ts filename="app/lib/definitions.ts" switcher
import * as z from 'zod'

export const SignupFormSchema = z.object({
  name: z
    .string()
    .min(2, { error: 'Name must be at least 2 characters long.' })
    .trim(),
  email: z.email({ error: 'Please enter a valid email.' }).trim(),
  password: z
    .string()
    .min(8, { error: 'Be at least 8 characters long' })
    .regex(/[a-zA-Z]/, { error: 'Contain at least one letter.' })
    .regex(/[0-9]/, { error: 'Contain at least one number.' })
    .regex(/[^a-zA-Z0-9]/, {
      error: 'Contain at least one special character.',
    })
    .trim(),
})

export type FormState =
  | {
      errors?: {
        name?: string[]
        email?: string[]
        password?: string[]
      }
      message?: string
    }
  | undefined
```

Để ngăn chặn các cuộc gọi không cần thiết đến API hoặc cơ sở dữ liệu của nhà cung cấp xác thực, bạn có thể `return` sớm trong Server Action nếu bất kỳ trường biểu mẫu nào không khớp với lược đồ đã xác định.

```ts filename="app/actions/auth.ts" switcher
import { SignupFormSchema, FormState } from '@/app/lib/definitions'

export async function signup(state: FormState, formData: FormData) {
  // Validate form fields
  const validatedFields = SignupFormSchema.safeParse({
    name: formData.get('name'),
    email: formData.get('email'),
    password: formData.get('password'),
  })

  // If any form fields are invalid, return early
  if (!validatedFields.success) {
    return {
      errors: validatedFields.error.flatten().fieldErrors,
    }
  }

  // Call the provider or db to create a user...
}
```

Quay lại `<SignupForm />` của bạn, bạn có thể sử dụng hook `useActionState` của React để hiển thị các lỗi xác thực trong khi biểu mẫu đang gửi:

```tsx filename="app/ui/signup-form.tsx" switcher highlight={7,15,21,27-36}
'use client'

import { signup } from '@/app/actions/auth'
import { useActionState } from 'react'

export default function SignupForm() {
  const [state, action, pending] = useActionState(signup, undefined)

  return (
    <form action={action}>
      <div>
        <label htmlFor="name">Name</label>
        <input id="name" name="name" placeholder="Name" />
      </div>
      {state?.errors?.name && <p>{state.errors.name}</p>}

      <div>
        <label htmlFor="email">Email</label>
        <input id="email" name="email" placeholder="Email" />
      </div>
      {state?.errors?.email && <p>{state.errors.email}</p>}

      <div>
        <label htmlFor="password">Password</label>
        <input id="password" name="password" type="password" />
      </div>
      {state?.errors?.password && (
        <div>
          <p>Password must:</p>
          <ul>
            {state.errors.password.map((error) => (
              <li key={error}>- {error}</li>
            ))}
          </ul>
        </div>
      )}
      <button disabled={pending} type="submit">
        Sign Up
      </button>
    </form>
  )
}
```

> **Thông tin hữu ích:**
>
> - Trong React 19, `useFormStatus` bao gồm các khóa bổ sung trên đối tượng trả về, như data, method, và action. Nếu bạn không sử dụng React 19, chỉ có khóa `pending` là khả dụng.
> - Trước khi thay đổi dữ liệu, bạn phải luôn đảm bảo người dùng cũng được ủy quyền để thực hiện hành động. Xem [Xác thực và Ủy quyền](#authorization).

#### 3. Tạo người dùng hoặc kiểm tra thông tin đăng nhập của người dùng

Sau khi xác thực các trường biểu mẫu, bạn có thể tạo tài khoản người dùng mới hoặc kiểm tra xem người dùng có tồn tại hay không bằng cách gọi API hoặc cơ sở dữ liệu của nhà cung cấp xác thực.

Tiếp tục từ ví dụ trước:

Sau khi tạo thành công tài khoản người dùng hoặc xác minh thông tin đăng nhập của người dùng, bạn có thể tạo một phiên để quản lý trạng thái xác thực của người dùng. Tùy thuộc vào chiến lược quản lý phiên của bạn, phiên có thể được lưu trữ trong cookie hoặc cơ sở dữ liệu, hoặc cả hai. Tiếp tục đến phần [Quản lý phiên](#session-management) để tìm hiểu thêm.

> **Mẹo:**
>
> - Ví dụ trên dài dòng vì nó chia nhỏ các bước xác thực cho mục đích giáo dục. Điều này làm nổi bật rằng việc triển khai giải pháp bảo mật của riêng bạn có thể nhanh chóng trở nên phức tạp. Hãy cân nhắc sử dụng [Thư viện xác thực](#auth-libraries) để đơn giản hóa quy trình.
> - Để cải thiện trải nghiệm người dùng, bạn có thể muốn kiểm tra các email hoặc tên người dùng trùng lặp sớm hơn trong luồng đăng ký. Ví dụ, khi người dùng nhập tên người dùng hoặc trường nhập liệu mất tiêu điểm. Điều này có thể giúp ngăn chặn việc gửi biểu mẫu không cần thiết và cung cấp phản hồi ngay lập tức cho người dùng. Bạn có thể debounce các yêu cầu với các thư viện như [use-debounce](https://www.npmjs.com/package/use-debounce) để quản lý tần suất của các kiểm tra này.

Dưới đây là các bước để triển khai biểu mẫu đăng ký và/hoặc đăng nhập:

1. Người dùng gửi thông tin đăng nhập của họ thông qua một biểu mẫu.
2. Biểu mẫu gửi một yêu cầu được xử lý bởi một API route.
3. Sau khi xác minh thành công, quy trình hoàn tất, cho biết người dùng đã xác thực thành công.
4. Nếu xác minh không thành công, một thông báo lỗi sẽ được hiển thị.

Hãy xem xét một biểu mẫu đăng nhập nơi người dùng có thể nhập thông tin đăng nhập của họ:

```tsx filename="pages/login.tsx" switcher
import { FormEvent } from 'react'
import { useRouter } from 'next/router'

export default function LoginPage() {
  const router = useRouter()

  async function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault()

    const formData = new FormData(event.currentTarget)
    const email = formData.get('email')
    const password = formData.get('password')

    const response = await fetch('/api/auth/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email, password }),
    })

    if (response.ok) {
      router.push('/profile')
    } else {
      // Handle errors
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" name="email" placeholder="Email" required />
      <input type="password" name="password" placeholder="Password" required />
      <button type="submit">Login</button>
    </form>
  )
}
```

Biểu mẫu trên có hai trường nhập liệu để nắm bắt email và mật khẩu của người dùng. Khi gửi, nó kích hoạt một hàm gửi yêu cầu POST đến một API route (`/api/auth/login`).

Sau đó, bạn có thể gọi API của Nhà cung cấp xác thực trong API route để xử lý xác thực:

```ts filename="pages/api/auth/login.ts" switcher
import type { NextApiRequest, NextApiResponse } from 'next'
import { signIn } from '@/auth'

export default async function handler(
  req: NextApiRequest,
  res: NextApiResponse
) {
  try {
    const { email, password } = req.body
    await signIn('credentials', { email, password })

    res.status(200).json({ success: true })
  } catch (error) {
    if (error.type === 'CredentialsSignin') {
      res.status(401).json({ error: 'Invalid credentials.' })
    } else {
      res.status(500).json({ error: 'Something went wrong.' })
    }
  }
}
```

## Quản lý phiên

Quản lý phiên đảm bảo rằng trạng thái đã xác thực của người dùng được bảo tồn qua các yêu cầu. Nó liên quan đến việc tạo, lưu trữ, làm mới và xóa các phiên hoặc mã thông báo (tokens).

Có hai loại phiên:

1. [**Không trạng thái (Stateless)**](#stateless-sessions): Dữ liệu phiên (hoặc mã thông báo) được lưu trữ trong cookie của trình duyệt. Cookie được gửi cùng với mỗi yêu cầu, cho phép phiên được xác minh trên server. Phương pháp này đơn giản hơn, nhưng có thể kém bảo mật hơn nếu không được triển khai chính xác.
2. [**Cơ sở dữ liệu (Database)**](#database-sessions): Dữ liệu phiên được lưu trữ trong cơ sở dữ liệu, với trình duyệt của người dùng chỉ nhận được ID phiên đã mã hóa. Phương pháp này bảo mật hơn, nhưng có thể phức tạp và sử dụng nhiều tài nguyên server hơn.

> **Thông tin hữu ích:** Mặc dù bạn có thể sử dụng một trong hai phương pháp, hoặc cả hai, chúng tôi khuyên bạn nên sử dụng thư viện quản lý phiên như [iron-session](https://github.com/vvo/iron-session) hoặc [Jose](https://github.com/panva/jose).

### Phiên không trạng thái (Stateless Sessions)

<AppOnly>

Để tạo và quản lý các phiên không trạng thái, có một vài bước bạn cần làm theo:

1. Tạo một khóa bí mật, sẽ được sử dụng để ký phiên của bạn, và lưu trữ nó như một [biến môi trường](/docs/app/guides/environment-variables).
2. Viết logic để mã hóa/giải mã dữ liệu phiên bằng thư viện quản lý phiên.
3. Quản lý cookie bằng API [`cookies`](/docs/app/api-reference/functions/cookies) của Next.js.

Ngoài những điều trên, hãy cân nhắc thêm chức năng để [cập nhật (hoặc làm mới)](#updating-or-refreshing-sessions) phiên khi người dùng quay lại ứng dụng, và [xóa](#deleting-the-session) phiên khi người dùng đăng xuất.

> **Thông tin hữu ích:** Kiểm tra xem [thư viện xác thực](#auth-libraries) của bạn có bao gồm quản lý phiên hay không.

#### 1. Tạo khóa bí mật

Có một vài cách bạn có thể tạo khóa bí mật để ký phiên của mình. Ví dụ, bạn có thể chọn sử dụng lệnh `openssl` trong terminal của mình:

```bash filename="terminal"
openssl rand -base64 32
```

Lệnh này tạo ra một chuỗi ngẫu nhiên 32 ký tự mà bạn có thể sử dụng làm khóa bí mật và lưu trữ trong [file biến môi trường](/docs/app/guides/environment-variables) của bạn:

```bash filename=".env"
SESSION_SECRET=your_secret_key
```

Sau đó, bạn có thể tham chiếu khóa này trong logic quản lý phiên của mình:

```js filename="app/lib/session.js"
const secretKey = process.env.SESSION_SECRET
```

#### 2. Mã hóa và giải mã phiên

Tiếp theo, bạn có thể sử dụng [thư viện quản lý phiên](#session-management-libraries) ưa thích của mình để mã hóa và giải mã các phiên. Tiếp tục từ ví dụ trước, chúng tôi sẽ sử dụng [Jose](https://www.npmjs.com/package/jose) (tương thích với [Edge Runtime](/docs/app/api-reference/edge)) và gói [`server-only`](https://www.npmjs.com/package/server-only) của React để đảm bảo rằng logic quản lý phiên của bạn chỉ được thực thi trên server.

```tsx filename="app/lib/session.ts" switcher
import 'server-only'
import { SignJWT, jwtVerify } from 'jose'
import { SessionPayload } from '@/app/lib/definitions'

const secretKey = process.env.SESSION_SECRET
const encodedKey = new TextEncoder().encode(secretKey)

export async function encrypt(payload: SessionPayload) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt()
    .setExpirationTime('7d')
    .sign(encodedKey)
}

export async function decrypt(session: string | undefined = '') {
  try {
    const { payload } = await jwtVerify(session, encodedKey, {
      algorithms: ['HS256'],
    })
    return payload
  } catch (error) {
    console.log('Failed to verify session')
  }
}
```

#### 3. Thiết lập cookie (tùy chọn được đề xuất)

Để lưu trữ phiên trong cookie, hãy sử dụng API [`cookies`](/docs/app/api-reference/functions/cookies) của Next.js. Cookie nên được đặt trên server, và bao gồm các tùy chọn được đề xuất:

- **HttpOnly**: Ngăn JavaScript phía client truy cập cookie.
- **Secure**: Sử dụng https để gửi cookie.
- **SameSite**: Chỉ định xem cookie có thể được gửi với các yêu cầu chéo trang hay không.
- **Max-Age hoặc Expires**: Xóa cookie sau một khoảng thời gian nhất định.
- **Path**: Xác định đường dẫn URL cho cookie.

Vui lòng tham khảo [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies) để biết thêm thông tin về từng tùy chọn này.

```ts filename="app/lib/session.ts" switcher
import 'server-only'
import { cookies } from 'next/headers'

export async function createSession(userId: string) {
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)
  const session = await encrypt({ userId, expiresAt })
  const cookieStore = await cookies()

  cookieStore.set('session', session, {
    httpOnly: true,
    secure: true,
    expires: expiresAt,
    sameSite: 'lax',
    path: '/',
  })
}
```

### Phiên cơ sở dữ liệu (Database Sessions)

Để tạo và quản lý các phiên cơ sở dữ liệu, bạn cần làm theo các bước sau:

1. Tạo một bảng trong cơ sở dữ liệu của bạn để lưu trữ phiên và dữ liệu (hoặc kiểm tra xem Thư viện xác thực của bạn có xử lý việc này không).
2. Triển khai chức năng để chèn, cập nhật và xóa các phiên.
3. Mã hóa ID phiên trước khi lưu trữ nó trong trình duyệt của người dùng, và đảm bảo cơ sở dữ liệu và cookie được đồng bộ hóa (điều này là tùy chọn, nhưng được khuyến nghị cho các kiểm tra xác thực lạc quan trong [Proxy](#optimistic-checks-with-proxy-optional)).

<AppOnly>

Ví dụ:

```ts filename="app/lib/session.ts" switcher

import { encrypt } from '@/app/lib/session'

    .values({
      userId: id,

  const session = await encrypt({ sessionId, expiresAt })

  // 3. Store the session in cookies for optimistic auth checks
  const cookieStore = await cookies()
  cookieStore.set('session', session, {
    httpOnly: true,
    secure: true,
    expires: expiresAt,
    sameSite: 'lax',
    path: '/',
  })
}
```

## Ủy quyền (Authorization)

Khi người dùng đã được xác thực và một phiên được tạo, bạn có thể triển khai ủy quyền để kiểm soát những gì người dùng có thể truy cập và thực hiện trong ứng dụng của bạn.

Có hai loại kiểm tra ủy quyền chính:

1. **Lạc quan (Optimistic)**: Kiểm tra xem người dùng có được ủy quyền truy cập một route hoặc thực hiện một hành động bằng cách sử dụng dữ liệu phiên được lưu trữ trong cookie hay không. Các kiểm tra này hữu ích cho các hoạt động nhanh chóng, chẳng hạn như hiển thị/ẩn các thành phần UI hoặc chuyển hướng người dùng dựa trên quyền hoặc vai trò.
2. **Bảo mật (Secure)**: Kiểm tra xem người dùng có được ủy quyền truy cập một route hoặc thực hiện một hành động bằng cách sử dụng dữ liệu phiên được lưu trữ trong cơ sở dữ liệu hay không. Các kiểm tra này bảo mật hơn và được sử dụng cho các hoạt động yêu cầu quyền truy cập vào dữ liệu nhạy cảm hoặc các hành động.

Đối với cả hai trường hợp, chúng tôi khuyên bạn nên:

- Tạo một [Lớp truy cập dữ liệu (DAL)](#creating-a-data-access-layer-dal) để tập trung logic ủy quyền của bạn
- Sử dụng [Đối tượng chuyển giao dữ liệu (DTO)](#using-data-transfer-objects-dto) để chỉ trả về dữ liệu cần thiết
- Tùy chọn sử dụng [Proxy](#optimistic-checks-with-proxy-optional) để thực hiện các kiểm tra lạc quan.

### Kiểm tra lạc quan với Proxy (Tùy chọn)

Có một số trường hợp bạn có thể muốn sử dụng [Proxy](/docs/app/api-reference/file-conventions/proxy) và chuyển hướng người dùng dựa trên quyền:

- Để thực hiện các kiểm tra lạc quan. Vì Proxy chạy trên mọi route, đó là một cách tốt để tập trung logic chuyển hướng và lọc trước những người dùng không được ủy quyền.
- Để bảo vệ các static routes chia sẻ dữ liệu giữa các người dùng (ví dụ: nội dung đằng sau paywall).

Tuy nhiên, vì Proxy chạy trên mọi route, bao gồm các routes [được prefetch](/docs/app/getting-started/linking-and-navigating#prefetching), điều quan trọng là chỉ đọc phiên từ cookie (kiểm tra lạc quan), và tránh kiểm tra cơ sở dữ liệu để ngăn chặn các vấn đề hiệu suất.

Ví dụ:

```tsx filename="proxy.ts" switcher
import { NextRequest, NextResponse } from 'next/server'
import { decrypt } from '@/app/lib/session'
import { cookies } from 'next/headers'

// 1. Specify protected and public routes
const protectedRoutes = ['/dashboard']
const publicRoutes = ['/login', '/signup', '/']

export default async function proxy(req: NextRequest) {
  // 2. Check if the current route is protected or public
  const path = req.nextUrl.pathname
  const isProtectedRoute = protectedRoutes.includes(path)
  const isPublicRoute = publicRoutes.includes(path)

  // 3. Decrypt the session from the cookie
  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)

  // 4. Redirect to /login if the user is not authenticated
  if (isProtectedRoute && !session?.userId) {
    return NextResponse.redirect(new URL('/login', req.nextUrl))
  }

  // 5. Redirect to /dashboard if the user is authenticated
  if (
    isPublicRoute &&
    session?.userId &&
    !req.nextUrl.pathname.startsWith('/dashboard')
  ) {
    return NextResponse.redirect(new URL('/dashboard', req.nextUrl))
  }

  return NextResponse.next()
}

// Routes Proxy should not run on
export const config = {
  matcher: ['/((?!api|_next/static|_next/image|.*\\.png$).*)'],
}
```

Mặc dù Proxy có thể hữu ích cho các kiểm tra ban đầu, nó không nên là tuyến phòng thủ duy nhất của bạn trong việc bảo vệ dữ liệu của bạn. Phần lớn các kiểm tra bảo mật nên được thực hiện càng gần nguồn dữ liệu của bạn càng tốt, xem [Lớp truy cập dữ liệu](#creating-a-data-access-layer-dal) để biết thêm thông tin.

> **Mẹo**:
>
> - Trong Proxy, bạn cũng có thể đọc cookie bằng cách sử dụng `req.cookies.get('session').value`.
> - Proxy sử dụng [Edge Runtime](/docs/app/api-reference/edge), hãy kiểm tra xem thư viện xác thực và thư viện quản lý phiên của bạn có tương thích hay không.
> - Bạn có thể sử dụng thuộc tính `matcher` trong Proxy để chỉ định những routes nào Proxy nên chạy. Mặc dù vậy, đối với xác thực, khuyến nghị Proxy chạy trên tất cả các routes.

### Tạo một Lớp truy cập dữ liệu (DAL)

Chúng tôi khuyên bạn nên tạo một DAL để tập trung các yêu cầu dữ liệu và logic ủy quyền của bạn.

DAL nên bao gồm một hàm xác minh phiên của người dùng khi họ tương tác với ứng dụng của bạn. Ít nhất, hàm nên kiểm tra xem phiên có hợp lệ hay không, sau đó chuyển hướng hoặc trả về thông tin người dùng cần thiết để thực hiện các yêu cầu tiếp theo.

Ví dụ, tạo một file riêng biệt cho DAL của bạn bao gồm một hàm `verifySession()`. Sau đó sử dụng API [cache](https://react.dev/reference/react/cache) của React để ghi nhớ giá trị trả về của hàm trong một lần render React:

```tsx filename="app/lib/dal.ts" switcher
import 'server-only'

import { cookies } from 'next/headers'
import { decrypt } from '@/app/lib/session'

export const verifySession = cache(async () => {
  const cookie = (await cookies()).get('session')?.value
  const session = await decrypt(cookie)

  if (!session?.userId) {
    redirect('/login')
  }

  return { isAuth: true, userId: session.userId }
})
```

```js filename="app/lib/dal.js" switcher
import 'server-only'

```

Sau đó, bạn có thể gọi hàm `verifySession()` trong các yêu cầu dữ liệu, Server Actions, Route Handlers của bạn:

```tsx filename="app/lib/dal.ts" switcher
export const getUser = cache(async () => {
  const session = await verifySession()
  if (!session) return null

  try {
    const data = await db.query.users.findMany({
      where: eq(users.id, session.userId),
      // Explicitly return the columns you need rather than the whole user object
      columns: {
        id: true,
        name: true,
        email: true,
      },
    })

    const user = data[0]

    return user
  } catch (error) {
    console.log('Failed to fetch user')
    return null
  }
})
```

> **Mẹo**:
>
> - Một DAL có thể được sử dụng để bảo vệ dữ liệu được fetch tại request time. Tuy nhiên, đối với các static routes chia sẻ dữ liệu giữa các người dùng, dữ liệu sẽ được fetch tại build time và không phải tại request time. Sử dụng [Proxy](#optimistic-checks-with-proxy-optional) để bảo vệ các static routes.
> - Đối với các kiểm tra bảo mật, bạn có thể kiểm tra xem phiên có hợp lệ hay không bằng cách so sánh ID phiên với cơ sở dữ liệu của bạn. Sử dụng hàm [cache](https://react.dev/reference/react/cache) của React để tránh các yêu cầu trùng lặp không cần thiết đến cơ sở dữ liệu trong một lần render.
> - Bạn có thể muốn hợp nhất các yêu cầu dữ liệu liên quan trong một lớp JavaScript chạy `verifySession()` trước bất kỳ phương thức nào.

### Sử dụng Đối tượng chuyển giao dữ liệu (DTO)

Khi truy xuất dữ liệu, bạn nên chỉ trả về dữ liệu cần thiết sẽ được sử dụng trong ứng dụng của mình, và không phải toàn bộ đối tượng. Ví dụ, nếu bạn đang fetch dữ liệu người dùng, bạn có thể chỉ trả về ID và tên của người dùng, thay vì toàn bộ đối tượng người dùng có thể chứa mật khẩu, số điện thoại, v.v.

Tuy nhiên, nếu bạn không kiểm soát cấu trúc dữ liệu trả về, hoặc đang làm việc trong một nhóm nơi bạn muốn tránh chuyển toàn bộ đối tượng cho client, bạn có thể sử dụng các chiến lược như chỉ định những trường nào an toàn để hiển thị cho client.

```tsx filename="app/lib/dto.ts" switcher
import 'server-only'
import { getUser } from '@/app/lib/dal'

function canSeeUsername(viewer: User) {
  return true
}

function canSeePhoneNumber(viewer: User, team: string) {
  return viewer.isAdmin || team === viewer.team
}

export async function getProfileDTO(slug: string) {
  const data = await db.query.users.findMany({
    where: eq(users.slug, slug),
    // Return specific columns here
  })
  const user = data[0]

  const currentUser = await getUser(user.id)

  // Or return only what's specific to the query here
  return {
    username: canSeeUsername(currentUser) ? user.username : null,
    phonenumber: canSeePhoneNumber(currentUser, user.team)
      ? user.phonenumber
      : null,
  }
}
```

Bằng cách tập trung các yêu cầu dữ liệu và logic ủy quyền của bạn trong một DAL và sử dụng DTOs, bạn có thể đảm bảo rằng tất cả các yêu cầu dữ liệu đều an toàn và nhất quán, giúp dễ dàng bảo trì, kiểm tra và gỡ lỗi khi ứng dụng của bạn mở rộng.

> **Thông tin hữu ích**:
>
> - Có một vài cách khác nhau bạn có thể xác định một DTO, từ việc sử dụng `toJSON()`, đến các hàm riêng lẻ như ví dụ trên, hoặc các lớp JS. Vì đây là các mẫu JavaScript và không phải là một tính năng React hoặc Next.js, chúng tôi khuyên bạn nên thực hiện một số nghiên cứu để tìm ra mẫu tốt nhất cho ứng dụng của bạn.
> - Tìm hiểu thêm về các phương pháp hay nhất về bảo mật trong [bài viết Bảo mật trong Next.js của chúng tôi](/blog/security-nextjs-server-components-actions).

### Server Components

Kiểm tra xác thực trong [Server Components](/docs/app/getting-started/server-and-client-components) rất hữu ích cho quyền truy cập dựa trên vai trò. Ví dụ, để render có điều kiện các components dựa trên vai trò của người dùng:

```tsx filename="app/dashboard/page.tsx" switcher
import { verifySession } from '@/app/lib/dal'

export default async function Dashboard() {
  const session = await verifySession()
  const userRole = session?.user?.role // Assuming 'role' is part of the session object

  if (userRole === 'admin') {
    return <AdminDashboard />
  } else if (userRole === 'user') {
    return <UserDashboard />
  } else {
    redirect('/login')
  }
}
```

```jsx filename="app/dashboard/page.jsx" switcher

Trong ví dụ này, chúng tôi sử dụng hàm `verifySession()` từ DAL của chúng tôi để kiểm tra các vai trò 'admin', 'user', và không được ủy quyền. Mẫu này đảm bảo rằng mỗi người dùng chỉ tương tác với các components phù hợp với vai trò của họ.

### Layouts và kiểm tra xác thực

Do [Partial Rendering](/docs/app/getting-started/linking-and-navigating#client-side-transitions), hãy thận trọng khi thực hiện các kiểm tra trong [Layouts](/docs/app/api-reference/file-conventions/layout) vì chúng không render lại khi điều hướng, có nghĩa là phiên người dùng sẽ không được kiểm tra trên mỗi thay đổi route.

Thay vào đó, bạn nên thực hiện các kiểm tra gần nguồn dữ liệu của bạn hoặc component sẽ được render có điều kiện.

Ví dụ, hãy xem xét một layout được chia sẻ fetch dữ liệu người dùng và hiển thị hình ảnh người dùng trong một nav. Thay vì thực hiện kiểm tra xác thực trong layout, bạn nên fetch dữ liệu người dùng (`getUser()`) trong layout và thực hiện kiểm tra xác thực trong DAL của bạn.

Điều này đảm bảo rằng bất cứ nơi nào `getUser()` được gọi trong ứng dụng của bạn, kiểm tra xác thực được thực hiện, và ngăn chặn các nhà phát triển quên kiểm tra người dùng được ủy quyền truy cập dữ liệu.

  )
}

Mẫu này **không được khuyến nghị** vì các ứng dụng Next.js có nhiều điểm vào, điều này sẽ không ngăn chặn các phân đoạn route lồng nhau và Server Actions bị truy cập.

### Server Actions

Xử lý [Server Actions](/docs/app/getting-started/updating-data) với cùng các cân nhắc bảo mật như các API endpoints công khai, và xác minh xem người dùng có được phép thực hiện một thay đổi hay không.

Trong ví dụ dưới đây, chúng tôi kiểm tra vai trò của người dùng trước khi cho phép hành động tiếp tục:

```ts filename="app/lib/actions.ts" switcher
'use server'
import { verifySession } from '@/app/lib/dal'

export async function serverAction(formData: FormData) {
  const session = await verifySession()
  const userRole = session?.user?.role

  // Return early if user is not authorized to perform the action
  if (userRole !== 'admin') {
    return null
  }

  // Proceed with the action for authorized users
}

### Route Handlers

Xử lý [Route Handlers](/docs/app/api-reference/file-conventions/route) với cùng các cân nhắc bảo mật như các API endpoints công khai, và xác minh xem người dùng có được phép truy cập Route Handler hay không.

Ví dụ:

```ts filename="app/api/route.ts" switcher
import { verifySession } from '@/app/lib/dal'

export async function GET() {
  // User authentication and role verification
  const session = await verifySession()

  // Check if the user is authenticated
  if (!session) {
    // User is not authenticated
    return new Response(null, { status: 401 })
  }

  // Check if the user has the 'admin' role
  if (session.user.role !== 'admin') {
    // User is authenticated but does not have the right permissions
    return new Response(null, { status: 403 })
  }

  // Continue for authorized users
}
```

```js filename="app/api/route.js" switcher

Ví dụ trên minh họa một Route Handler với kiểm tra bảo mật hai cấp. Đầu tiên nó kiểm tra một phiên hoạt động, và sau đó xác minh xem người dùng đã đăng nhập có phải là một 'admin' hay không.

Điều này hoạt động, nhưng bất kỳ Server Components con nào sẽ được render trên server trước, và sẽ không có quyền truy cập vào dữ liệu phiên của context provider:

#### Bảo vệ API Routes

API Routes trong Next.js rất cần thiết để xử lý logic phía server và quản lý dữ liệu. Điều quan trọng là phải bảo mật các routes này để đảm bảo rằng chỉ những người dùng được ủy quyền mới có thể truy cập các chức năng cụ thể. Điều này thường liên quan đến việc xác minh trạng thái xác thực của người dùng và quyền dựa trên vai trò của họ.

  // ... implementation of the API Route
