Next.js đi kèm với TypeScript tích hợp sẵn, tự động cài đặt các gói cần thiết và định cấu hình cài đặt phù hợp khi bạn tạo dự án mới với `create-next-app`.

Để thêm TypeScript vào một dự án hiện có, hãy đổi tên tệp thành `.ts` / `.tsx`. Chạy `next dev` và `next build` để tự động cài đặt các phụ thuộc cần thiết và thêm tệp `tsconfig.json` với các tùy chọn cấu hình được đề xuất.

> **Cần biết**: Nếu bạn đã có tệp `jsconfig.json`, hãy sao chép tùy chọn trình biên dịch `paths` từ `jsconfig.json` cũ vào tệp `tsconfig.json` mới và xóa tệp `jsconfig.json` cũ.

## Plugin IDE

Next.js bao gồm một plugin TypeScript và trình kiểm tra kiểu (type checker) tùy chỉnh, mà VSCode và các trình soạn thảo mã khác có thể sử dụng để kiểm tra kiểu nâng cao và tự động hoàn thành.

Bạn có thể bật plugin trong VS Code bằng cách:

1. Mở command palette (`Ctrl/⌘` + `Shift` + `P`)
2. Tìm kiếm "TypeScript: Select TypeScript Version"
3. Chọn "Use Workspace Version"

## An toàn kiểu End-to-End

Next.js App Router có **tính an toàn kiểu nâng cao**. Điều này bao gồm:

1. **Không tuần tự hóa dữ liệu giữa hàm fetching và page**: Bạn có thể `fetch` trực tiếp trong các components, layouts, và pages trên server. Dữ liệu này _không_ cần phải được tuần tự hóa (chuyển đổi thành chuỗi) để được chuyển sang phía client để sử dụng trong React. Thay vào đó, vì `app` sử dụng Server Components theo mặc định, chúng ta có thể sử dụng các giá trị như `Date`, `Map`, `Set`, và nhiều hơn nữa mà không cần bất kỳ bước bổ sung nào. Trước đây, bạn cần phải nhập thủ công ranh giới giữa server và client với các kiểu dành riêng cho Next.js.
2. **Luồng dữ liệu hợp lý giữa các components**: Với việc loại bỏ `_app` để ủng hộ root layouts, giờ đây việc hình dung luồng dữ liệu giữa các components và pages trở nên dễ dàng hơn. Trước đây, dữ liệu chảy giữa các `pages` riêng lẻ và `_app` rất khó để định kiểu và có thể gây ra các lỗi khó hiểu. Với [colocated data fetching](/docs/app/getting-started/fetching-data) trong App Router, đây không còn là vấn đề nữa.

[Data Fetching trong Next.js](/docs/app/getting-started/fetching-data) hiện cung cấp tính an toàn kiểu end-to-end gần nhất có thể mà không quy định về lựa chọn cơ sở dữ liệu hoặc nhà cung cấp nội dung của bạn.

Chúng tôi có thể định kiểu dữ liệu phản hồi như bạn mong đợi với TypeScript thông thường. Ví dụ:

```tsx filename="app/page.tsx" switcher
async function getData() {
  const res = await fetch('https://api.example.com/...')
  // Giá trị trả về *không* được tuần tự hóa
  // Bạn có thể trả về Date, Map, Set, v.v.
  return res.json()
}

export default async function Page() {
  const name = await getData()

  return '...'
}
```

Để có tính an toàn kiểu end-to-end _hoàn chỉnh_, điều này cũng yêu cầu cơ sở dữ liệu hoặc nhà cung cấp nội dung của bạn hỗ trợ TypeScript. Điều này có thể thông qua việc sử dụng [ORM](https://en.wikipedia.org/wiki/Object%E2%80%93relational_mapping) hoặc trình tạo truy vấn an toàn kiểu (type-safe query builder).

## Ví dụ

### Kiểm tra kiểu Tệp cấu hình Next.js

Bạn có thể sử dụng TypeScript và import các kiểu trong cấu hình Next.js của mình bằng cách sử dụng `next.config.ts`.

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  /* tùy chọn cấu hình ở đây */
}

export default nextConfig
```

Phân giải mô-đun trong `next.config.ts` hiện bị giới hạn ở CommonJS. Tuy nhiên, cú pháp ECMAScript Modules (ESM) có sẵn khi [sử dụng trình phân giải TypeScript gốc của Node.js](#using-nodejs-native-typescript-resolver-for-nextconfigts) cho Node.js v22.10.0 trở lên.

Khi sử dụng tệp `next.config.js`, bạn có thể thêm một số kiểm tra kiểu trong IDE của mình bằng cách sử dụng JSDoc như bên dưới:

```js filename="next.config.js"
// @ts-check

/** @type {import('next').NextConfig} */
const nextConfig = {
  /* tùy chọn cấu hình ở đây */
}

module.exports = nextConfig
```

### Sử dụng Trình phân giải TypeScript gốc của Node.js cho `next.config.ts`

> **Lưu ý**: Có sẵn trên Node.js v22.10.0+ và chỉ khi tính năng được bật. Next.js không bật nó.

Next.js phát hiện [trình phân giải TypeScript gốc của Node.js](https://nodejs.org/api/typescript.html) qua [`process.features.typescript`](https://nodejs.org/api/process.html#processfeaturestypescript), được thêm vào trong **v22.10.0**. Khi hiện diện, `next.config.ts` có thể sử dụng ESM gốc, bao gồm `await` cấp cao nhất và `import()` động. Cơ chế này kế thừa các khả năng và hạn chế của trình phân giải của Node.

Trong các phiên bản Node.js **v22.18.0+**, `process.features.typescript` được bật theo mặc định. Đối với các phiên bản giữa **v22.10.0** và **22.17.x**, hãy chọn tham gia với `NODE_OPTIONS=--experimental-transform-types`:

```bash filename="Terminal"
NODE_OPTIONS=--experimental-transform-types next <command>
```

#### Đối với các dự án CommonJS (Mặc định)

Mặc dù `next.config.ts` hỗ trợ cú pháp ESM gốc trên các dự án CommonJS, Node.js vẫn sẽ giả định `next.config.ts` là tệp CommonJS theo mặc định, dẫn đến việc Node.js phân tích lại tệp dưới dạng ESM khi phát hiện cú pháp mô-đun. Do đó, chúng tôi khuyên bạn nên sử dụng tệp `next.config.mts` cho các dự án CommonJS để chỉ rõ ràng đó là một mô-đun ESM:

```ts filename="next.config.mts"
import type { NextConfig } from 'next'

// Top-level await và dynamic import được hỗ trợ
const flags = await import('./flags.js').then((m) => m.default ?? m)

const nextConfig: NextConfig = {
  /* tùy chọn cấu hình ở đây */
  typedRoutes: Boolean(flags?.typedRoutes),
}

export default nextConfig
```

#### Đối với các dự án ESM

Khi `"type"` được đặt thành `"module"` trong `package.json`, dự án của bạn sử dụng ESM. Tìm hiểu thêm về cài đặt này [trong tài liệu Node.js](https://nodejs.org/api/packages.html#type). Trong trường hợp này, bạn có thể viết `next.config.ts` trực tiếp với cú pháp ESM.

> **Cần biết**: Khi sử dụng `"type": "module"` trong `package.json` của bạn, tất cả các tệp `.js` và `.ts` trong dự án của bạn được coi là các mô-đun ESM theo mặc định. Bạn có thể cần đổi tên các tệp có cú pháp CommonJS thành phần mở rộng `.cjs` hoặc `.cts` nếu cần.

### Liên kết được định kiểu tĩnh (Statically Typed Links)

Next.js có thể định kiểu tĩnh các liên kết để ngăn chặn lỗi chính tả và các lỗi khác khi sử dụng `next/link`, cải thiện tính an toàn kiểu khi điều hướng giữa các trang.

Hoạt động trong cả Pages và App Router cho prop `href` trong `next/link`. Trong App Router, nó cũng định kiểu các phương thức `next/navigation` như `push`, `replace`, và `prefetch`. Nó không định kiểu các phương thức `next/router` trong Pages Router.

Các chuỗi `href` literal được xác thực, trong khi các `href` không phải literal có thể yêu cầu ép kiểu với `as Route`.

Để chọn tham gia tính năng này, `typedRoutes` cần được bật và dự án cần sử dụng TypeScript.

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typedRoutes: true,
}

export default nextConfig
```

Next.js sẽ tạo một định nghĩa liên kết trong `.next/types` chứa thông tin về tất cả các routes hiện có trong ứng dụng của bạn, mà TypeScript sau đó có thể sử dụng để cung cấp phản hồi trong trình chỉnh sửa của bạn về các liên kết không hợp lệ.

> **Cần biết**: Nếu bạn thiết lập dự án của mình mà không có `create-next-app`, hãy đảm bảo các kiểu Next.js đã tạo được bao gồm bằng cách thêm `.next/types/**/*.ts` vào mảng `include` trong `tsconfig.json` của bạn:

{/* prettier-ignore-start */}

```json filename="tsconfig.json" highlight={4}
{
  "include": [
    "next-env.d.ts",
    ".next/types/**/*.ts",
    "**/*.ts",
    "**/*.tsx"
  ],
  "exclude": ["node_modules"]
}
```
{/* prettier-ignore-end */}

Hiện tại, hỗ trợ bao gồm bất kỳ chuỗi literal nào, bao gồm cả các phân đoạn động. Đối với các chuỗi không phải literal, bạn cần ép kiểu thủ công với `as Route`. Ví dụ dưới đây cho thấy cả cách sử dụng `next/link` và `next/navigation`:

```tsx filename="app/example-client.tsx"
'use client'

import type { Route } from 'next'
import Link from 'next/link'
import { useRouter } from 'next/navigation'

export default function Example() {
  const router = useRouter()
  const slug = 'nextjs'

  return (
    <>
      {/* Link: literal và dynamic */}
      <Link href="/about" />
      <Link href={`/blog/${slug}`} />
      <Link href={('/blog/' + slug) as Route} />
      {/* Lỗi TypeScript nếu href không phải là một route hợp lệ */}
      <Link href="/aboot" />

      {/* Router: chuỗi literal và dynamic được xác thực */}
      <button onClick={() => router.push('/about')}>Push About</button>
      <button onClick={() => router.replace(`/blog/${slug}`)}>
        Replace Blog
      </button>
      <button onClick={() => router.prefetch('/contact')}>
        Prefetch Contact
      </button>

      {/* Đối với chuỗi không phải literal, ép kiểu thành Route */}
      <button onClick={() => router.push(('/blog/' + slug) as Route)}>
        Push Non-literal Blog
      </button>
    </>
  )
}
```

Điều tương tự cũng áp dụng cho việc chuyển hướng các routes được xác định bởi proxy:

```ts filename="proxy.ts"
import { NextRequest, NextResponse } from 'next/server'

export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname === '/proxy-redirect') {
    return NextResponse.redirect(new URL('/', request.url))
  }

  return NextResponse.next()
}
```

```tsx filename="app/some/page.tsx"
import type { Route } from 'next'

export default function Page() {
  return <Link href={'/proxy-redirect' as Route}>Link Text</Link>
}
```

Để chấp nhận `href` trong một thành phần tùy chỉnh bao bọc `next/link`, hãy sử dụng generic:

```tsx
import type { Route } from 'next'
import Link from 'next/link'

function Card<T extends string>({ href }: { href: Route<T> | URL }) {
  return (
    <Link href={href}>
      <div>My Card</div>
    </Link>
  )
}
```

Bạn cũng có thể định kiểu một cấu trúc dữ liệu đơn giản và lặp lại để render các liên kết:

```ts filename="components/nav-items.ts"
import type { Route } from 'next'

type NavItem<T extends string = string> = {
  href: T
  label: string
}

export const navItems: NavItem<Route>[] = [
  { href: '/', label: 'Home' },
  { href: '/about', label: 'About' },
  { href: '/blog', label: 'Blog' },
]
```

Sau đó, map qua các items để render `Link`s:

```tsx filename="components/nav.tsx"
import Link from 'next/link'
import { navItems } from './nav-items'

export function Nav() {
  return (
    <nav>
      {navItems.map((item) => (
        <Link key={item.href} href={item.href}>
          {item.label}
        </Link>
      ))}
    </nav>
  )
}
```

> **Nó hoạt động như thế nào?**
>
> Khi chạy `next dev` hoặc `next build`, Next.js tạo một tệp `.d.ts` ẩn bên trong `.next` chứa thông tin về tất cả các routes hiện có trong ứng dụng của bạn (tất cả các routes hợp lệ như kiểu `href` của `Link`). Tệp `.d.ts` này được bao gồm trong `tsconfig.json` và trình biên dịch TypeScript sẽ kiểm tra `.d.ts` đó và cung cấp phản hồi trong trình chỉnh sửa của bạn về các liên kết không hợp lệ.

### Type IntelliSense cho Biến môi trường

Trong quá trình phát triển, Next.js tạo một tệp `.d.ts` trong `.next/types` chứa thông tin về các biến môi trường đã tải cho IntelliSense của trình chỉnh sửa của bạn. Nếu cùng một khóa biến môi trường được xác định trong nhiều tệp, nó sẽ được loại bỏ trùng lặp theo [Thứ tự tải Biến môi trường](/docs/app/guides/environment-variables#environment-variable-load-order).

Để chọn tham gia tính năng này, `experimental.typedEnv` cần được bật và dự án cần sử dụng TypeScript.

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    typedEnv: true,
  },
}

export default nextConfig
```

> **Cần biết**: Các kiểu được tạo dựa trên các biến môi trường được tải tại thời điểm chạy phát triển, điều này loại trừ các biến từ các tệp `.env.production*` theo mặc định. Để bao gồm các biến dành riêng cho production, hãy chạy `next dev` với `NODE_ENV=production`.

### Static Generation và Server-side Rendering

Đối với [`getStaticProps`](/docs/pages/api-reference/functions/get-static-props), [`getStaticPaths`](/docs/pages/api-reference/functions/get-static-paths), và [`getServerSideProps`](/docs/pages/api-reference/functions/get-server-side-props), bạn có thể sử dụng các kiểu `GetStaticProps`, `GetStaticPaths`, và `GetServerSideProps` tương ứng:

```tsx filename="pages/blog/[slug].tsx"
import type { GetStaticProps, GetStaticPaths, GetServerSideProps } from 'next'

export const getStaticProps = (async (context) => {
  // ...
}) satisfies GetStaticProps

export const getStaticPaths = (async () => {
  // ...
}) satisfies GetStaticPaths

export const getServerSideProps = (async (context) => {
  // ...
}) satisfies GetServerSideProps
```

> **Cần biết:** `satisfies` đã được thêm vào TypeScript trong [4.9](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-9.html). Chúng tôi khuyên bạn nên nâng cấp lên phiên bản mới nhất của TypeScript.

### Với API Routes

Sau đây là một ví dụ về cách sử dụng các kiểu tích hợp sẵn cho API routes:

```ts filename="pages/api/hello.ts"
import type { NextApiRequest, NextApiResponse } from 'next'

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  res.status(200).json({ name: 'John Doe' })
}
```

Bạn cũng có thể định kiểu dữ liệu phản hồi:

```ts filename="pages/api/hello.ts"
import type { NextApiRequest, NextApiResponse } from 'next'

type Data = {
  name: string
}

export default function handler(
  req: NextApiRequest,
  res: NextApiResponse<Data>
) {
  res.status(200).json({ name: 'John Doe' })
}
```

### Với `App` tùy chỉnh

Nếu bạn có một [`App` tùy chỉnh](/docs/pages/building-your-application/routing/custom-app), bạn có thể sử dụng kiểu tích hợp sẵn `AppProps` và thay đổi tên tệp thành `./pages/_app.tsx` như sau:

```ts
import type { AppProps } from 'next/app'

export default function MyApp({ Component, pageProps }: AppProps) {
  return <Component {...pageProps} />
}
```

### Kiểm tra kiểu tăng dần (Incremental type checking)

Kể từ `v10.2.1` Next.js hỗ trợ [kiểm tra kiểu tăng dần](https://www.typescriptlang.org/tsconfig#incremental) khi được bật trong `tsconfig.json` của bạn, điều này có thể giúp tăng tốc độ kiểm tra kiểu trong các ứng dụng lớn hơn.

### Đường dẫn `tsconfig` tùy chỉnh

Trong một số trường hợp, bạn có thể muốn sử dụng cấu hình TypeScript khác cho các bản build hoặc công cụ. Để làm điều đó, hãy đặt `typescript.tsconfigPath` trong `next.config.ts` để trỏ Next.js đến một tệp `tsconfig` khác.

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typescript: {
    tsconfigPath: 'tsconfig.build.json',
  },
}

export default nextConfig
```

Ví dụ, chuyển sang cấu hình khác cho các bản build production:

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const isProd = process.env.NODE_ENV === 'production'

const nextConfig: NextConfig = {
  typescript: {
    tsconfigPath: isProd ? 'tsconfig.build.json' : 'tsconfig.json',
  },
}

export default nextConfig
```

<details>
<summary>Tại sao bạn có thể sử dụng `tsconfig` riêng cho các bản build</summary>

Bạn có thể cần nới lỏng các kiểm tra trong các tình huống như monorepos, nơi bản build cũng xác thực các phụ thuộc được chia sẻ không khớp với tiêu chuẩn dự án của bạn, hoặc khi nới lỏng các kiểm tra trong CI để tiếp tục phân phối trong khi di chuyển cục bộ sang các cài đặt TypeScript nghiêm ngặt hơn (và vẫn muốn IDE của bạn làm nổi bật việc sử dụng sai).

Ví dụ, nếu dự án của bạn sử dụng `useUnknownInCatchVariables` nhưng một số phụ thuộc monorepo vẫn giả định `any`:

```json filename="tsconfig.build.json"
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "useUnknownInCatchVariables": false
  }
}
```

Điều này giữ cho trình chỉnh sửa của bạn nghiêm ngặt thông qua `tsconfig.json` trong khi cho phép bản build production sử dụng các cài đặt nới lỏng.

</details>

> **Cần biết**:
>
> - Các IDE thường đọc `tsconfig.json` để chẩn đoán và IntelliSense, vì vậy bạn vẫn có thể thấy cảnh báo IDE trong khi các bản build production sử dụng cấu hình thay thế. Phản chiếu các tùy chọn quan trọng nếu bạn muốn sự tương đương trong trình chỉnh sửa.
> - Trong quá trình phát triển, chỉ `tsconfig.json` được theo dõi các thay đổi. Nếu bạn chỉnh sửa tên tệp khác thông qua `typescript.tsconfigPath`, hãy khởi động lại máy chủ dev để áp dụng các thay đổi.
> - Tệp được định cấu hình được sử dụng trong `next dev`, `next build`, và `next typegen`.

### Vô hiệu hóa lỗi TypeScript trong production

Next.js làm hỏng **bản build production** (`next build`) của bạn khi có lỗi TypeScript trong dự án của bạn.

Nếu bạn muốn Next.js tạo mã production một cách nguy hiểm ngay cả khi ứng dụng của bạn có lỗi, bạn có thể vô hiệu hóa bước kiểm tra kiểu tích hợp sẵn.

Nếu bị vô hiệu hóa, hãy chắc chắn rằng bạn đang chạy kiểm tra kiểu như một phần của quy trình build hoặc deploy của mình, nếu không điều này có thể rất nguy hiểm.

Mở `next.config.ts` và bật tùy chọn `ignoreBuildErrors` trong cấu hình `typescript`:

```ts filename="next.config.ts"
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typescript: {
    // !! CẢNH BÁO !!
    // Nguy hiểm cho phép các bản build production hoàn thành thành công ngay cả khi
    // dự án của bạn có lỗi kiểu.
    // !! CẢNH BÁO !!
    ignoreBuildErrors: true,
  },
}

export default nextConfig
```

> **Cần biết**: Bạn có thể chạy `tsc --noEmit` để tự kiểm tra lỗi TypeScript trước khi build. Điều này hữu ích cho các đường ống CI/CD nơi bạn muốn kiểm tra lỗi TypeScript trước khi triển khai.

### Khai báo kiểu tùy chỉnh

Khi bạn cần khai báo các kiểu tùy chỉnh, bạn có thể bị cám dỗ sửa đổi `next-env.d.ts`. Tuy nhiên, tệp này được tạo tự động, vì vậy mọi thay đổi bạn thực hiện sẽ bị ghi đè. Thay vào đó, bạn nên tạo một tệp mới, hãy gọi nó là `new-types.d.ts`, và tham chiếu nó trong `tsconfig.json` của bạn:

```json filename="tsconfig.json"
{
  "compilerOptions": {
    "skipLibCheck": true
    //...bị cắt bớt...
  },
  "include": [
    "new-types.d.ts",
    "next-env.d.ts",
    ".next/types/**/*.ts",
    "**/*.ts",
    "**/*.tsx"
  ],
  "exclude": ["node_modules"]
}
```
