## Sử dụng

Hỗ trợ thử nghiệm cho việc inlining CSS trong `<head>`. Khi cờ này được bật, tất cả những nơi chúng tôi thường tạo thẻ `<link>` sẽ thay vào đó có thẻ `<style>` được tạo.

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    inlineCss: true,
  },
}

export default nextConfig
```

```js filename="next.config.js" switcher
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    inlineCss: true,
  },
}

module.exports = nextConfig
```

## Đánh đổi

### Khi nào nên sử dụng Inline CSS

Inlining CSS có thể có lợi trong một số trường hợp:

- **Khách truy cập lần đầu**: Vì các file CSS là tài nguyên chặn hiển thị (render-blocking), việc inlining loại bỏ độ trễ tải xuống ban đầu mà khách truy cập lần đầu gặp phải, cải thiện hiệu suất tải trang.

- **Các chỉ số hiệu suất**: Bằng cách loại bỏ các yêu cầu mạng bổ sung cho các file CSS, việc inlining có thể cải thiện đáng kể các chỉ số chính như First Contentful Paint (FCP) và Largest Contentful Paint (LCP).

- **Kết nối chậm**: Đối với người dùng trên các mạng chậm hơn, nơi mỗi yêu cầu thêm độ trễ đáng kể, inlining CSS có thể cung cấp sự gia tăng hiệu suất đáng chú ý bằng cách giảm các vòng lặp mạng (network roundtrips).

- **Atomic CSS Bundles (ví dụ: Tailwind)**: Với các framework utility-first như Tailwind CSS, kích thước của các styles cần thiết cho một trang thường là O(1) so với độ phức tạp của thiết kế. Điều này làm cho inlining trở thành một lựa chọn hấp dẫn vì toàn bộ tập hợp các styles cho trang hiện tại là nhẹ và không tăng theo kích thước trang. Inlining Tailwind styles đảm bảo payload tối thiểu và loại bỏ nhu cầu về các yêu cầu mạng bổ sung, điều này có thể nâng cao hiệu suất hơn nữa.

### Khi nào không nên sử dụng Inline CSS

Mặc dù inlining CSS mang lại những lợi ích đáng kể cho hiệu suất, nhưng có những trường hợp nó có thể không phải là lựa chọn tốt nhất:

- **Các gói CSS lớn**: Nếu gói CSS của bạn quá lớn, việc inlining nó có thể làm tăng đáng kể kích thước của HTML, dẫn đến Time to First Byte (TTFB) chậm hơn và hiệu suất có thể kém hơn đối với người dùng có kết nối chậm.
- **CSS động hoặc cụ thể cho trang**: Đối với các ứng dụng có styles rất động hoặc các trang sử dụng các bộ CSS khác nhau, việc inlining có thể dẫn đến dư thừa và phình to, vì toàn bộ CSS cho tất cả các trang có thể cần phải được inlined lặp đi lặp lại.

- **Browser Caching**: Trong trường hợp khách truy cập thường xuyên quay lại trang web của bạn, các file CSS bên ngoài cho phép trình duyệt cache các styles một cách hiệu quả, giảm chuyển dữ liệu cho các lần truy cập tiếp theo. Inlining CSS loại bỏ lợi ích này.

Đánh giá cẩn thận các sự đánh đổi này, và xem xét kết hợp inlining với các chiến lược khác, chẳng hạn như trích xuất critical CSS hoặc một cách tiếp cận lai, để có kết quả tốt nhất phù hợp với nhu cầu của trang web của bạn.

> **Cần biết**:
>
> Tính năng này hiện đang là thử nghiệm và có một số hạn chế đã biết:
>
> - CSS inlining được áp dụng toàn cầu và không thể được cấu hình trên cơ sở từng trang
> - Styles bị trùng lặp trong quá trình tải trang ban đầu - một lần trong các thẻ `<style>` cho SSR và một lần trong RSC payload
> - Khi điều hướng đến các trang được render tĩnh, styles sẽ sử dụng các thẻ `<link>` thay vì inline CSS để tránh trùng lặp
> - Tính năng này không có sẵn trong chế độ development và chỉ hoạt động trong các bản build production
