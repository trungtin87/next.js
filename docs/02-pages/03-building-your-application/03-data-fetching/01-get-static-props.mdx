Nếu bạn export một hàm có tên `getStaticProps` (Static Site Generation) từ một trang, Next.js sẽ pre-render trang này tại thời điểm build bằng cách sử dụng các props được trả về bởi `getStaticProps`.

```tsx filename="pages/index.tsx" switcher
import type { InferGetStaticPropsType, GetStaticProps } from 'next'

type Repo = {
  name: string
  stargazers_count: number
}

export const getStaticProps = (async (context) => {
  const res = await fetch('https://api.github.com/repos/vercel/next.js')
  const repo = await res.json()
  return { props: { repo } }
}) satisfies GetStaticProps<{
  repo: Repo
}>

export default function Page({
  repo,
}: InferGetStaticPropsType<typeof getStaticProps>) {
  return repo.stargazers_count
}
```

```jsx filename="pages/index.js" switcher
export async function getStaticProps() {
  const res = await fetch('https://api.github.com/repos/vercel/next.js')
  const repo = await res.json()
  return { props: { repo } }
}

export default function Page({ repo }) {
  return repo.stargazers_count
}
```

> Lưu ý rằng bất kể loại rendering nào, bất kỳ `props` nào cũng sẽ được truyền cho page component và có thể được xem trên phía client trong HTML ban đầu. Điều này để cho phép trang được [hydrated](https://react.dev/reference/react-dom/hydrate) một cách chính xác. Đảm bảo rằng bạn không truyền bất kỳ thông tin nhạy cảm nào không nên có sẵn trên client trong `props`.

[Tài liệu tham khảo API `getStaticProps`](/docs/pages/api-reference/functions/get-static-props) bao gồm tất cả các tham số và props có thể được sử dụng với `getStaticProps`.

## Khi nào tôi nên sử dụng getStaticProps?

Bạn nên sử dụng `getStaticProps` nếu:

- Dữ liệu cần thiết để render trang có sẵn tại thời điểm build trước khi có request của người dùng
- Dữ liệu đến từ một headless CMS
- Trang phải được pre-rendered (cho SEO) và rất nhanh — `getStaticProps` tạo ra các tệp `HTML` và `JSON`, cả hai đều có thể được cache bởi CDN để có hiệu suất tốt
- Dữ liệu có thể được cache công khai (không dành riêng cho người dùng). Điều kiện này có thể được bỏ qua trong một số tình huống cụ thể bằng cách sử dụng Proxy để viết lại đường dẫn.

## Khi nào getStaticProps chạy

`getStaticProps` luôn chạy trên server và không bao giờ chạy trên client. Bạn có thể xác thực mã được viết bên trong `getStaticProps` đã bị xóa khỏi bundle phía client [với công cụ này](https://next-code-elimination.vercel.app/).

- `getStaticProps` luôn chạy trong quá trình `next build`
- `getStaticProps` chạy trong background khi sử dụng [`fallback: true`](/docs/pages/api-reference/functions/get-static-paths#fallback-true)
- `getStaticProps` được gọi trước khi render ban đầu khi sử dụng [`fallback: blocking`](/docs/pages/api-reference/functions/get-static-paths#fallback-blocking)
- `getStaticProps` chạy trong background khi sử dụng `revalidate`
- `getStaticProps` chạy on-demand trong background khi sử dụng [`revalidate()`](/docs/pages/guides/incremental-static-regeneration#on-demand-revalidation-with-revalidatepath)

Khi kết hợp với [Incremental Static Regeneration](/docs/pages/guides/incremental-static-regeneration), `getStaticProps` sẽ chạy trong background trong khi trang cũ đang được revalidate, và trang mới được phục vụ cho trình duyệt.

`getStaticProps` không có quyền truy cập vào request đến (như query parameters hoặc HTTP headers) vì nó tạo ra HTML tĩnh. Nếu bạn cần truy cập vào request cho trang của mình, hãy xem xét sử dụng [Proxy](/docs/pages/api-reference/file-conventions/proxy) ngoài `getStaticProps`.

## Sử dụng getStaticProps để fetch data từ CMS

Ví dụ sau đây cho thấy cách bạn có thể fetch một danh sách các bài đăng blog từ CMS.

```tsx filename="pages/blog.tsx" switcher
// posts sẽ được điền vào tại thời điểm build bởi getStaticProps()
export default function Blog({ posts }) {
  return (
    <ul>
      {posts.map((post) => (
        <li>{post.title}</li>
      ))}
    </ul>
  )
}

// Hàm này được gọi tại thời điểm build trên server-side.
// Nó sẽ không được gọi trên client-side, vì vậy bạn thậm chí có thể thực hiện
// các truy vấn database trực tiếp.
export async function getStaticProps() {
  // Gọi một API endpoint bên ngoài để lấy posts.
  // Bạn có thể sử dụng bất kỳ thư viện data fetching nào
  const res = await fetch('https://.../posts')
  const posts = await res.json()

  // Bằng cách trả về { props: { posts } }, component Blog
  // sẽ nhận `posts` như một prop tại thời điểm build
  return {
    props: {
      posts,
    },
  }
}
```

## Viết mã server-side trực tiếp

Vì `getStaticProps` chỉ chạy trên server-side, nó sẽ không bao giờ chạy trên client-side. Nó thậm chí sẽ không được bao gồm trong bundle JS cho trình duyệt, vì vậy bạn có thể viết các truy vấn database trực tiếp mà không cần gửi chúng đến trình duyệt.

Điều này có nghĩa là thay vì fetch một **API route** từ `getStaticProps` (bản thân nó fetch data từ một nguồn bên ngoài), bạn có thể viết mã server-side trực tiếp trong `getStaticProps`.

Lấy ví dụ sau. Một API route được sử dụng để fetch một số dữ liệu từ CMS. API route đó sau đó được gọi trực tiếp từ `getStaticProps`. Điều này tạo ra một cuộc gọi bổ sung, làm giảm hiệu suất. Thay vào đó, logic để fetch dữ liệu từ CMS có thể được chia sẻ bằng cách sử dụng thư mục `lib/`. Sau đó nó có thể được chia sẻ với `getStaticProps`.

```js filename="lib/load-posts.js"
// Hàm sau được chia sẻ
// với getStaticProps và API routes
// từ thư mục `lib/`
export async function loadPosts() {
  // Gọi một API endpoint bên ngoài để lấy posts
  const res = await fetch('https://.../posts/')
  const data = await res.json()

  return data
}
```

```jsx filename="pages/blog.js"
// pages/blog.js
import { loadPosts } from '../lib/load-posts'

// Hàm này chỉ chạy trên server side
export async function getStaticProps() {
  // Thay vì fetch `/api` route của bạn, bạn có thể gọi cùng một
  // hàm trực tiếp trong `getStaticProps`
  const posts = await loadPosts()

  // Props được trả về sẽ được truyền cho page component
  return { props: { posts } }
}
```

Ngoài ra, nếu bạn **không** sử dụng API routes để fetch data, thì API [`fetch()`](https://developer.mozilla.org/docs/Web/API/Fetch_API) _có thể_ được sử dụng trực tiếp trong `getStaticProps` để fetch data.

Để xác minh những gì Next.js loại bỏ khỏi bundle phía client, bạn có thể sử dụng [công cụ next-code-elimination](https://next-code-elimination.vercel.app/).

## Tạo tĩnh cả HTML và JSON

Khi một trang với `getStaticProps` được pre-rendered tại thời điểm build, ngoài tệp HTML của trang, Next.js tạo ra một tệp JSON chứa kết quả của việc chạy `getStaticProps`.

Tệp JSON này sẽ được sử dụng trong client-side routing thông qua [`next/link`](/docs/pages/api-reference/components/link) hoặc [`next/router`](/docs/pages/api-reference/functions/use-router). Khi bạn điều hướng đến một trang được pre-rendered bằng `getStaticProps`, Next.js fetch tệp JSON này (được tính toán trước tại thời điểm build) và sử dụng nó làm props cho page component. Điều này có nghĩa là các chuyển đổi trang phía client sẽ **không** gọi `getStaticProps` vì chỉ có JSON được export được sử dụng.

Khi sử dụng Incremental Static Generation, `getStaticProps` sẽ được thực thi trong background để tạo ra JSON cần thiết cho client-side navigation. Bạn có thể thấy điều này dưới dạng nhiều request được thực hiện cho cùng một trang, tuy nhiên, điều này được dự định và không có tác động đến hiệu suất người dùng cuối.

## Tôi có thể sử dụng getStaticProps ở đâu

`getStaticProps` chỉ có thể được export từ một **page**. Bạn **không thể** export nó từ các tệp không phải page, `_app`, `_document`, hoặc `_error`.

Một trong những lý do cho hạn chế này là React cần có tất cả dữ liệu cần thiết trước khi trang được render.

Ngoài ra, bạn phải sử dụng export `getStaticProps` như một hàm độc lập — nó sẽ **không** hoạt động nếu bạn thêm `getStaticProps` như một thuộc tính của page component.

> **Nên biết**: nếu bạn đã tạo một [custom app](/docs/pages/building-your-application/routing/custom-app), hãy đảm bảo bạn đang truyền `pageProps` cho page component như được hiển thị trong tài liệu được liên kết, nếu không props sẽ trống.

Trong development (`next dev`), `getStaticProps` sẽ được gọi trên mọi request.

## Preview Mode

Bạn có thể tạm thời bỏ qua static generation và render trang tại **thời điểm request** thay vì thời điểm build bằng cách sử dụng [**Preview Mode**](/docs/pages/guides/preview-mode). Ví dụ, bạn có thể đang sử dụng một headless CMS và muốn xem trước các bản nháp trước khi chúng được xuất bản.
